# 05 流式输出性能优化

> 本篇是流式性能方案的**汇总与延伸**：`doc/01` 展开讲 SSE 链路与双协议适配，`doc/02` 展开讲块级增量渲染的推导与证明，这里不重复那两篇的细节，只把散落在六层里的优化点收成一张表，并补上「还能怎么优化」的分析。异常处理见 `doc/06`。

## 1. 问题画像

一次长回复（约 3000 字 Markdown）会同时压上三条高频通路：

| 通路 | 频率 | 朴素实现的单次代价 | 朴素实现的总代价 |
| --- | --- | --- | --- |
| token 到达 → 更新正文 | 每秒数十次 | O(1) 字符串追加 | O(n) |
| 正文 → Markdown 解析 + 属性串 | 每次到达一次 | O(已生成长度) | **O(n²)** |
| 属性串 → TextKit 排版 + 行高测量 | 每次到达一次 | O(已生成长度) | **O(n²)** |

两处 O(n²) 的根源是同一个：**把「已生成的全部文本」当成每帧的输入**。回复越长，每帧越慢，用户在回复后半段会看到明显掉帧——这是流式聊天 App 最典型的性能形态。

本项目的整体思路是三道闸门，依次把每帧的输入量压到有界：

```
网络 delta ──[闸门1: 合帧]── 每帧最多处理一次
           ──[闸门2: 块级切分]── 每帧只碰最后一个未闭合块
           ──[闸门3: 双层缓存]── 已闭合块的属性串与高度只算一次
```

## 2. 已落地的技术方案

### 2.1 网络层

**① 按字节缓冲增量解析 SSE**
`SSEEventParser` 缓冲的是 `[UInt8]` 而不是 `String`（[SSEEventParser.swift:12](WBChatApp-UIKit/Core/Networking/SSEEventParser.swift:12)）。

- *为什么*：UTF-8 多字节字符会被 TCP 分包从中劈开，按 `String` 缓冲会在拼接点解出 `U+FFFD` 替换字符，而且这个错误不可逆。按字节缓冲让「粘包 / 分包 / `\n`·`\r\n`·`\r` 三种换行跨回调」三类边界全部在解析器内部收口（[:27](WBChatApp-UIKit/Core/Networking/SSEEventParser.swift:27)）。
- *代价*：逐字节喂入有函数调用开销，但换来了可以逐字节做属性测试的纯函数，正确性收益远大于这点开销。

**② 传输层不懂业务语义，超时分四类**
`SSEStream` 只负责状态码校验与字节喂给解析器；协议语义交给 adapter（[SSEStream.swift:60](WBChatApp-UIKit/Core/Networking/SSEStream.swift:60)）。超时拆成四个独立维度（[:10](WBChatApp-UIKit/Core/Networking/SSEStream.swift:10)）：

| 超时 | 默认值 | 守的是什么 |
| --- | --- | --- |
| `networkIdleTimeout` | 60s | 连接还在但一个字节都不来 |
| `semanticProgressTimeout` | 180s | 字节在来（心跳帧），但一个 token 都不出 |
| `totalTimeout` | 600s | 兜底，防止无限流 |
| `usageTailTimeout` | 2s | 已拿到 `finishReason`，再等一下 usage 帧 |
| `pollingInterval` | 100ms | 超时检测的轮询粒度 |

- *为什么分开*：只有网络空闲超时的实现，面对「服务端每 10s 发一个 `: ping` 注释帧但模型已经卡死」这种情况会永远等下去。语义进度超时由 `SemanticStreamProgress` actor 维护，只有真的吐出非空 token 才刷新（[NetworkChatProvider.swift:165](WBChatApp-UIKit/Core/LLM/NetworkChatProvider.swift:165)）。
- *代价*：100ms 轮询的常驻 Task，对电量影响可忽略；换来的是四类卡死都能在确定时间内收敛。

**③ 取消一路传到 `URLSession`**
`AsyncBytes` 的迭代被取消**不保证**释放仍打开的 HTTP 请求，所以用 `defer { bytes.task.cancel() }` + `withTaskCancellationHandler` 双重保险（[SSEStream.swift:86](WBChatApp-UIKit/Core/Networking/SSEStream.swift:86)、[:101](WBChatApp-UIKit/Core/Networking/SSEStream.swift:101)）。

- *为什么重要*：用户点「停止」后连接不断，服务端会继续计费并占用连接池；多次停止/重发会堆积僵尸连接，表现为「越用越慢」。

**④ 历史上下文裁剪**
请求只带最近 20 条消息，且过滤掉状态不是 `completed` 的助手消息（[ChatGenerationCoordinator.swift:157](WBChatApp-UIKit/Core/Generation/ChatGenerationCoordinator.swift:157)）。

- *为什么*：请求体直接决定首字节延迟与 prompt token 成本；把失败/中断的半截回复发回去还会污染上下文。

### 2.2 合帧层（闸门 1）

**⑤ `CADisplayLink` 对齐屏幕刷新率合帧**
网络增量只更新内存快照，`.content` 事件在 ViewModel 里直接 `break` 什么都不做（[ChatViewModel.swift:100](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:100)）；真正的排版发生在 `DisplayLinkThrottle` 的每帧回调里（[StreamThrottle.swift:13](WBChatApp-UIKit/Features/Chat/StreamThrottle.swift:13) → [ChatViewModel.swift:181](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:181)）。

- *为什么用 `CADisplayLink` 而不是 `Timer`*：它天然与 60/120Hz 刷新节奏对齐，「每帧最多一次排版、最多一次贴底滚动」这个上界是机制保证的，不需要手调间隔；`Timer` 要么过密（白做）要么过疏（视觉卡顿）。
- *代价*：token 的显示会延迟最多一帧（8~16ms），人眼不可察。
- *可测性*：抽成 `StreamThrottling` 协议，测试可以手动驱动 tick，不依赖真实屏幕刷新。

**⑥ 切后台停合帧**
进入后台时停掉 display link，回前台重新 `loadHistory()` 重建（[ChatViewModel.swift:88](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:88)）。后台排版是纯浪费，且会消耗宝贵的后台执行预算。

### 2.3 切块层（闸门 2）

**⑦ 只处理完整行 + 已闭合块只增不改**
`StreamingBlockSplitter` 的尾部残行永远留在 `partial` 里，连同它所属的块以 open 形式输出；`sealedBlocks` 随流推进**只增不改**（[StreamingBlockSplitter.swift:14](WBChatApp-UIKit/Core/Markdown/StreamingBlockSplitter.swift:14)、[:32](WBChatApp-UIKit/Core/Markdown/StreamingBlockSplitter.swift:32)）。

- *为什么这是地基*：有了这条不变量，上层才敢把已闭合块的属性串与高度**永久缓存**，总代价从 O(n²) 降到 O(n)。没有它，任何缓存都可能在下一帧被推翻。
- *代价*：纯值语义、无 UI 依赖，可以逐字符喂入做属性测试（`StreamingBlockSplitterTests`）；代价是状态机本身要处理列表空行挂起、CRLF 跨帧、段落被块起始行打断等一堆边界，代码复杂度集中在这个文件里。

**⑧ 按块解析，代码块绕开解析器**
`AttributedRenderer.render` 每次只把**一个块**喂给 swift-markdown（[AttributedRenderer.swift:23](WBChatApp-UIKit/Core/Markdown/AttributedRenderer.swift:23)）；代码块完全不走解析器，走自写的线性扫描高亮（[:25](WBChatApp-UIKit/Core/Markdown/AttributedRenderer.swift:25)）。

- *为什么代码块特殊*：① 省一次解析；② 未闭合的围栏在标准 Markdown 里不是合法代码块，走解析器会出图错乱，自写扫描可以边写边高亮。
- `CodeHighlighter` 用一遍线性扫描而不是正则（[CodeHighlighter.swift:16](WBChatApp-UIKit/Core/Markdown/CodeHighlighter.swift:16)）：注释与字符串会「吞掉」内部内容，天然避免「字符串里的 `func` 被标成关键字」，也避免正则回溯的最坏情况。

### 2.4 缓存层（闸门 3）

**⑨ 属性串缓存只存已闭合块，且跨消息共享**
`AttributedCache.attributedString` 对 `isSealed == false` 的块直接透传渲染、不写缓存（[AttributedCache.swift:33](WBChatApp-UIKit/Core/Markdown/AttributedCache.swift:33)）——未闭合块每帧都在变，缓存它既无意义还会撑爆内存。缓存键 `cacheKey` 刻意**不含 ordinal**（[MarkdownBlock.swift:33](WBChatApp-UIKit/Core/Markdown/MarkdownBlock.swift:33)），所以内容相同的块可以跨消息、跨会话命中。底层是 `NSCache`，`countLimit = 400`，内存压力下由系统自动回收。

**⑩ 高度按「块内容 + 量化宽度」缓存**
`AttributedCache.height` 的二级键是量化后的宽度（[AttributedCache.swift:56](WBChatApp-UIKit/Core/Markdown/AttributedCache.swift:56)、[:90](WBChatApp-UIKit/Core/Markdown/AttributedCache.swift:90)）。

- *为什么要量化*：宽度来自 safe area 与 Auto Layout 的浮点运算，两次算出的值可能只差一个 ulp。直接拿浮点数当字典键，这种误差会让高度缓存**静默失效**——不报错，只表现为反复重新测量、性能莫名变差。按屏幕像素粒度（固定 3，覆盖 @1x/@2x/@3x）取整后再做键。
- *为什么不用 `UIScreen.main.scale`*：iOS 17+ 已标记 deprecated，而且把缓存行为绑死在运行环境上，不利于测试与推理。

### 2.5 视图层

**⑪a TextKit 2 增量追加排版**
两个块视图都经 `UITextView.applyIncrementally(_:)` 更新文本（[IncrementalTextApply.swift](WBChatApp-UIKit/Features/Chat/Views/IncrementalTextApply.swift)）：用 `NSTextContentStorage.performEditingTransaction` 只替换与旧内容发散的尾部，而不是整体 `attributedText =`，TextKit 2 的排版失效范围随之收缩到尾部。

- *发散点怎么定*：`AttributedPrefix.stableLength` 比对新旧属性串的字符与属性 run，取完全相同的最长前缀。**不能靠 Markdown 语义猜**——`前**粗` 补上闭合星号后，前面那几个字符会从普通文字变成加粗，前缀的属性是会被追溯改写的。只比对渲染结果本身，正确性由构造保证：最坏退化成全量替换，不存在「以为稳定其实不稳定」。
- *代价为什么可控*：属性 run 数量很少（一个段落通常 1~10 个），所以属性比对是 O(run 数)；字符前缀比对 O(n)，与「本来就要把整个属性串构建出来」同阶。
- *一个坑*：返回的偏移必须吸附到字位簇边界，否则会从代理对中间切开产生乱码。

**⑪ `applyPatch` 只重配置末尾未闭合块**
已闭合块的视图一旦建好就不再触碰（[BlockStackView.swift:70](WBChatApp-UIKit/Features/Chat/Views/BlockStackView.swift:70)）。上一帧的 open 块本帧闭合时，**复用同一个视图实例就地固化**，而不是回收重建——后者会在闭合瞬间产生可见闪动。

**⑫ 槽位级高度缓存，流式路径绝不整体清空**
`cachedHeights: [CGFloat?]` 与 `blockViews` 一一对应，`nil` 表示待重算（[BlockStackView.swift:230](WBChatApp-UIKit/Features/Chat/Views/BlockStackView.swift:230)、[:247](WBChatApp-UIKit/Features/Chat/Views/BlockStackView.swift:247)）。`appendView` 只给新槽位置 `nil`，`updateView` 只给自己那一个槽位置 `nil`，其余已闭合槽位原样保留；只有渲染宽度变化时才整体重建。

- *为什么单独强调*：这层局部缓存如果图省事每帧 `removeAll()`，第 ⑨⑩ 条那份「已闭合块只算一次」的承诺就被架空了——O(n²) 会从高度测量这一侧原路返回。这是实现时真实踩过的坑（代码注释里标为 I1）。

**⑬ 手写 `layoutSubviews` 代替 `UIStackView`**
[BlockStackView.swift:142](WBChatApp-UIKit/Features/Chat/Views/BlockStackView.swift:142) 自己算 y 轴累加。

- *为什么*：流式期间尾块高度每帧都变，走 Auto Layout 约束求解的代价远高于自己加一遍；而且块是竖排、宽度撑满，布局逻辑本身只有五行。
- *代价*：放弃了约束的声明式表达，新增块类型时要记得同时维护布局与高度两处——用 `BlockView` 协议统一 `heightThatFits(width:)` 接口来约束。

**⑭ 放弃 `automaticDimension`，自管行高缓存**
`ChatViewController` 实现 `heightForRowAt` + 按 messageID 索引的 `heightCache`（[ChatViewController.swift:563](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:563)）。

- *为什么*：`automaticDimension` 每帧要让 Auto Layout 重新求解**整条约束链**（包括所有没变化的已闭合块），正好把闸门 2、3 省下来的收益全吃掉。
- 高度变化只有超过 0.5pt 才惊动 tableView（[:322](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:322)），用裸的 `beginUpdates()/endUpdates()` 强制重新查询可见行行高——中间**不夹带任何**结构性 mutation。
- *已闭合块的那一次测量*：交给 `TextKitMeasurer`——一套无视图的 TextKit 2 栈，不需要活的 `UITextView`。用同一个排版引擎是为了让测出来的高度与实际渲染结构性一致（CoreText 方案实测差 0~3pt，见 `doc/02` 第 6 节）。
- *为什么不能用 `reloadRows`*：dataSource 是 `UITableViewDiffableDataSource`，iOS 15+ 直接调结构性 mutation API 会抛 `NSInternalInconsistencyException`，实测每发一条消息必崩（[:369](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:369) 的注释记录了这个事故）。低频的结构性刷新改走 `reconfigureItems`。

**⑮ 流式期间直接取 cell 实例打补丁**
`applyPatch` 走 `tableView.cellForRow` 拿到实例直接改，不走 diffable apply（[ChatViewController.swift:294](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:294)）。消息滚出可视区时只清高度缓存值、**不触发** `invalidateHeight` 的全量 diff 通道（[:303](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:303)，注释标为 I2）——否则流式消息一旦滚走，每帧都会触发一次全量 diff。

**⑯ `BlockViewPool` 按类型分桶复用 `UITextView`**
[BlockViewPool.swift:7](WBChatApp-UIKit/Features/Chat/Views/BlockViewPool.swift:7)，每类上限 12 个。

- *为什么必须按 kind 分桶*：`MarkdownTextBlockView` 与 `CodeBlockView` 内部都是 `UITextView`，但配置完全相反（后者 `widthTracksTextView = false` + 超大 `textContainer.size` 以支持横向滚动不换行），混在一个队列里会借出配置对不上的视图。`BlockView` 协议强制每个实现类声明 `static var viewKind`，新增类型时编译器会要求补上，不存在「忘了同步回收侧 switch」的可能。
- **离屏测量与共享池的相互作用**：`heightForRowAt` 的离屏测量用两个**常驻**测量 cell，而不是每次新建（[ChatViewController.swift:55](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:55)、[:577](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:577)）。每次 `configure` 前先 `prepareForReuse()` 把上次借走的块视图还给池子，做到收支平衡——否则临时 cell 被 ARC 释放时借走的视图永不归还，池子被逐渐掏空，复用机制退化成「只能不断新建」。`BlockViewPoolBalanceTests` 专门守这一点。

**⑰ 禁止访问 `layoutManager` / `textStorage`**
[MarkdownTextBlockView.swift:7](WBChatApp-UIKit/Features/Chat/Views/MarkdownTextBlockView.swift:7) 的类注释写明全类禁令。

- *为什么*：iOS 16+ 的 `UITextView` 默认由 TextKit 2 驱动，但只要碰一次这两个旧 API，UIKit 就会**静默回退** TextKit 1，而且没有任何警告。两套引擎在换行、断字上有细微行为差异，降级路径又没有文档，一旦发生只会表现为难以归因的排版变化。项目用 `usesTextKit2` 哨兵属性（[:41](WBChatApp-UIKit/Features/Chat/Views/MarkdownTextBlockView.swift:41)）+ 单测锁死。
- *要分清的一条界线*：触发降级的是 **`UITextView` 自己的** `layoutManager` / `textStorage`。⑪a 里用到的 `NSTextContentStorage.textStorage` 是 TextKit 2 的后备存储，不是一个东西，不会降级——哨兵测试在连续 20 次增量更新后仍然为真。

### 2.6 滚动层

**⑱ `AutoScrollController` 是纯计算状态机**
不持有 `UIScrollView`，所有判定都是纯函数（[AutoScrollController.swift:10](WBChatApp-UIKit/Features/Chat/AutoScrollController.swift:10)）。

- `detached` 态**完全不干预滚动**：内容在可视区下方增长时，用户正在看的内容视觉位置本就不动，什么都不做才是对的——省掉了每帧一次 `setContentOffset`。
- 只有向上拖才脱离贴底（向下拖是在追内容，不该打断）。
- 程序化滚动用**整数深度计数**而非布尔量（[:88](WBChatApp-UIKit/Features/Chat/AutoScrollController.swift:88)）：嵌套/重叠的两次程序化滚动中，布尔量会被第一次 `end` 提前解除保护，把后续的动画误判成用户滚动。

### 2.7 持久化层

**⑲ 写库全在独立串行队列 + 1s checkpoint**
`GenerationStore` 持有一个 `qos: .utility` 的串行队列（[ChatRepository.swift:189](WBChatApp-UIKit/Core/Persistence/ChatRepository.swift:189)）；流式期间按 1s 周期落库，而不是每个 delta 写一次（[ChatGenerationCoordinator.swift:169](WBChatApp-UIKit/Core/Generation/ChatGenerationCoordinator.swift:169)）。

- *为什么*：每个 delta 落库会在流式期间产生每秒数十次 SQLite 写事务，主线程还要等写完才能继续；1s 周期把写放大压到约 1/50，代价是崩溃时最多丢 1s 内容——这是明确接受的权衡（取舍理由见 `doc/06` 第 2 节）。

## 3. 贯穿全局的两条不变量

整篇优化可以压缩成两句话，面试时先说这两条，再按需展开细节：

> **I1：已闭合块只增不改。** 因此它的属性串与高度只会被计算一次。任何代码路径（切块、缓存、视图槽位、行高）都不得让已闭合块重算——`BlockStackView` 里专门有 `assertionFailure` 守这条契约（[BlockStackView.swift:102](WBChatApp-UIKit/Features/Chat/Views/BlockStackView.swift:102)）。
>
> **I2：每帧最多一次排版、最多一次贴底。** 由 `CADisplayLink` 的节奏机制保证，与 token 到达频率解耦。

两条叠加的效果：**每帧的工作量只与「最后一个未闭合块」的长度有关，与回复总长度无关。**

## 4. 还能优化的地方

以下按「收益 ÷ 改动成本」排序。**排序依据是复杂度分析，不是实测**——真机数据采集方法见第 5 节。

### 4.1 每帧仍有一条 O(已生成长度) 的主线程路径（收益最高）

`ChatViewModel.flush()` 每帧做三件 O(n) 的事（[ChatViewModel.swift:181](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:181)）：

1. 调 `coordinator.snapshot()`，而它会拷贝整个 `messages` 数组（含全部正文字符串，[ChatGenerationCoordinator.swift:86](WBChatApp-UIKit/Core/Generation/ChatGenerationCoordinator.swift:86)）；
2. `last.content.hasPrefix(renderedText)` 做前缀校验；
3. `dropFirst(renderedText.count)` 取出 delta。

**这是目前唯一仍随回复长度线性增长的每帧开销**，等于在闸门 2、3 之前留了一道没关严的门。Swift 的 String 是 COW，拷贝数组本身不复制字符内容，所以实际代价主要在 2、3 两步的字符遍历，但它确实随 n 增长。

- **改法**：让 coordinator 在 `.content` 事件里直接携带本次 delta 与一个单调递增的内容版本号；ViewModel 比对版本号而不是比对字符串，拿到的 delta 直接喂给 splitter。`resetSplitter` 的「前缀不匹配就重置」逻辑改为「版本号不连续就重置」。
- **风险**：需要同时改 coordinator 的事件定义与 ViewModel 的重置判定，`ChatViewModelTests` 里的手动驱动测试要跟着改。

### 4.2 未闭合块的长度无上界

闸门 2 保证「每帧只处理一个块」，但**没有保证这个块有多大**。三种内容会让单块长度无界：

- 无空行的长段落（模型常见输出形态）；
- 长表格（只要行都以 `|` 开头就一直不闭合）；
- 长代码块（围栏闭合前整块都是 open）。

这三种情况下，每帧要对整块重新 `render` + 测量。代码块尤其重：

- `CodeBlockView.heightThatFits` 用 `greatestFiniteMagnitude` 宽度测不换行的全量代码（[CodeBlockView.swift:131](WBChatApp-UIKit/Features/Chat/Views/CodeBlockView.swift:131)）；
- `CodeHighlighter` 每帧两次 O(n) 分配：`Array(code)` 与 `utf16Offsets`（[CodeHighlighter.swift:55](WBChatApp-UIKit/Core/Markdown/CodeHighlighter.swift:55)）。

- **改法（两条可独立做）**：① **行级软封**——把 open 块内部「已经完整的行」当作可缓存子单元，每帧只重排最后一行，属性串用 `NSMutableAttributedString` 追加而非重建；② **高度估算**——未闭合代码块的高度按「行数 × 行高」算，只在闭合瞬间精确测量一次。
- **风险**：①要在 splitter 之下再引入一层粒度，复杂度明显上升，建议先用实测数据确认长代码块真的是瓶颈再做；②简单得多，但「估算值与精确值在闭合瞬间跳变」会让视图抖一下，需要让估算足够准（等宽字体行高是常量，可行）。

> **已部分落地。** ①的「属性串追加而非重建」已经做了，分两层：
>
> - **排版层**：`UITextView.applyIncrementally(_:)` 经 `performEditingTransaction` 只替换与旧内容发散的尾部，TextKit 2 的排版失效范围随之收缩。发散点由 `AttributedPrefix.stableLength` 给出——不靠 Markdown 语义猜哪段稳定（行内语法会追溯改写前面的渲染），而是直接比对新旧属性串的字符与属性 run，正确性由构造保证。
> - **高亮层**：`CodeHighlighter.scan` 在扫描时报出「最后一个安全切点」，`AttributedRenderer` 据此记一条前缀记忆，下一帧只扫新增部分。安全切点的定义是「某行行首且不在任何跨行结构内部」——跨行的有两种，块注释，以及**遇到行尾反斜杠会跨过换行继续吃下一行的字符串**（这条最初漏了，是实现时才发现的）。
>
> 仍然没做的是②的高度估算，以及段落类块的解析增量化（`AttributedRenderer.render` 对未闭合段落仍每帧全量跑一次 swift-markdown）。
>
> 另需说明：高亮层这一条是**常数级而非渐进级**优化。省掉的是分词（`Array(code)` 的字位簇拆分、UTF-16 偏移表、逐字符扫描），但每帧仍有一次 `hasPrefix` 比较和一次前缀属性串拷贝，都还是 O(n)。真实收益待实测确认，不划算就整条回退。

### 4.3 行高缓存与 cell 重配的失效粒度过粗

`applySnapshot` 里两处全量操作（[ChatViewController.swift:266](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:266)、[:267](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:267)）：

```swift
snapshot.reconfigureItems(state.messages.map(\.id).filter { existing.contains($0) })
heightCache.removeAll()
```

任何 `state` 变化都会触发——包括流式起止、`canSend` 翻转、`hasUnsavedContent` 变化。长会话里每次状态跳变就让**所有行**重新离屏测量一遍。注意 `state` 的 `didSet` 有 `state != oldValue` 去重（[ChatViewModel.swift:28](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:28)），所以流式期间不会每帧触发，但发送/结束/重试这些时刻会。

- **改法**：diff 出真正变化的 messageID（状态、errorText、重试按钮可见性）只失效这几行；`heightCache` 改为按 id 删除而非 `removeAll()`。
- **风险**：低。属于纯粹的失效粒度收窄，行为不变。

### 4.4 `displayReasoning(for:)` 在高频路径上重复 snapshot + 线性查找

[ChatViewModel.swift:129](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:129) 每次调用都 `snapshot()` 一次再 `first { $0.id == messageID }` 线性查找，而它被 cellProvider（[ChatViewController.swift:188](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:188)）和离屏测量（[:592](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:592)）各调一次，都在 `heightForRowAt` 的热路径上。`displayText(for:)` 同理。

- **改法**：直接读 ViewModel 已有的 `state.messages`（它已经带了 `reasoning` 字段），不回查 coordinator；若要 O(1)，再加一份 `[String: Int]` 的 id→下标索引。
- **风险**：低。注意 `displayText` 的语义是「流式期间也要拿到最新正文」，改之前确认 `state.messages[].text` 确实是最新快照（目前 `apply()` 里是从 snapshot 映射的，是最新的）。

### 4.5 思考过程每帧全量写 `UILabel.text`

`ReasoningSectionView.setText` 无论折叠与否都整体赋值（[ReasoningSectionView.swift:43](WBChatApp-UIKit/Features/Chat/Views/ReasoningSectionView.swift:43)），而 reasoning 的增量和正文一样走每帧通路（[ChatViewModel.swift:192](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:192)）。推理模型的思考内容常常比正文还长，这里等于绕过了闸门 2、3 的全部优化——`UILabel` 每帧对全量文本重排一次。

折叠态的高度已经短路了（`heightThatFits` 直接返回 `headerHeight`），但 `bodyLabel.text` 的赋值与随之而来的 `setNeedsLayout` 仍在发生。

- **改法（成本递增）**：① 折叠态只存字符串、不写 `bodyLabel.text`，展开时一次性同步——改动极小，覆盖最常见场景（默认折叠）；② 展开态下让 reasoning 也走块级增量那套（splitter + cache），代价是要再配一套渲染管线。
- **风险**：①低，注意展开瞬间要补一次同步；②中。

### 4.6 `cacheKey` 的哈希碰撞是静默错误

[MarkdownBlock.swift:33](WBChatApp-UIKit/Core/Markdown/MarkdownBlock.swift:33) 用 `Hasher().finalize()` 的 `Int` 作为缓存唯一键。碰撞时 `AttributedCache` 会返回**另一个块**的属性串——不崩溃、不报错，只是显示错内容，而且 Swift 的 `Hasher` 每次进程启动有随机种子，同一条输入在不同次运行里碰撞行为不同，极难复现。

这是正确性问题而非性能问题，但修它几乎零成本，所以放在这里一起提。

- **改法**：`Entry` 里存一份 `kind` + `rawText`，命中后比对；不等就按 miss 处理重新渲染。64 位空间下碰撞概率极低，这一步比对的开销可忽略。
- **风险**：极低。

### 4.7 历史消息一次性全量加载 + 全量切块

`loadHistory()` 读整个会话的消息，再对**每一条**助手消息跑一遍 `splitWhole`（[ChatViewModel.swift:114](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:114)、[:197](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:197)）。切块本身是 O(总字数)，加上 `viewWillAppear` 里还会 `tableView.layoutIfNeeded()` 同步布局一次（[ChatViewController.swift:94](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:94)），几百条消息的会话打开时会有可感知的卡顿。而且 `loadHistory` 在从后台恢复时还会再跑一次（[ChatViewModel.swift:96](WBChatApp-UIKit/Features/Chat/ChatViewModel.swift:96)）。

- **改法**：① 按 ordinal 倒序分页读取（先读最近 30 条，上滑加载更多）；② 切块改为懒执行——`blocks(for:)` 第一次被问到时才切，结果缓存。②单独做就能消掉大部分开销，且不用改 UI。
- **风险**：①要处理「分页 + 贴底恢复阅读位置」的交互，中等；②低。

### 4.8 已闭合块的渲染仍全在主线程

`AttributedRenderer.render` 是纯函数（不碰 UI 状态，只构造 `NSAttributedString`），理论上可以在块闭合的瞬间丢到后台预渲染 + 预测高度，主线程后续只取缓存。

- **改法**：在 `BlockPatch.newlySealed` 到达时，把渲染与测量派发到后台队列，写入 `AttributedCache`；主线程命中缓存即可。
- **风险**：中高。`AttributedCache` 当前明确约定「所有调用都在主线程，内部不加锁」（[AttributedCache.swift:8](WBChatApp-UIKit/Core/Markdown/AttributedCache.swift:8)），`Entry.heights` 是裸字典，跨线程读写会数据竞争甚至崩溃。要动这条路径必须先给缓存加锁或改成 actor，而加锁本身在主线程命中路径上也有成本——**建议先实测确认主线程渲染真的是瓶颈，再决定是否付这个复杂度**。另外 `UIFont` 相关 API 的线程安全性需要逐个确认。
- **新增的同类约束**：`TextKitMeasurer` 复用同一套 TextKit 对象，`AttributedRenderer` 的代码块前缀记忆也是可变状态，两者都和 `AttributedCache` 一样是「只在主线程调用、内部不加锁」。要把渲染或测量挪到后台，这三处得一起解决，不能只改一个。

### 4.10 cell 级测高仍然依赖活视图（二期）

块级测高已经不需要视图了，但 `AssistantMessageCell.heightThatFits` 还要量 `reasoningView`、`errorLabel`、「重新生成」按钮，`UserMessageCell` 还要量气泡里的 `UILabel`。所以 `ChatViewController` 的两个常驻测量 cell（[:55](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:55)）和 `BlockViewPoolBalanceTests` 守着的那套收支平衡逻辑都还在。

- **改法**：把这几处 `UILabel` 的测量也换成无视图测量，然后给 `BlockStackView` 加一个「只按 `[MarkdownBlock]` 算高度、不建视图」的类型方法，`measureHeight(for:width:)` 就不再需要 cell 实例。
- **风险**：中。`UILabel` 与 TextKit 2 的尺寸是否一致需要先用同一套 parity 测试验证过，不能假定；`UserMessageCell` 的气泡还有 `maxWidthRatio` 与内边距要一并搬。

### 4.9 贴底每帧都 `setContentOffset`

`stickToBottomIfNeeded` 在 pinned 态每帧调用一次（[ChatViewController.swift:423](WBChatApp-UIKit/Features/Chat/ChatViewController.swift:423)），即使这一帧的内容高度没变（例如 delta 只是在当前行末尾追加几个字符、行数没增加）。

- **改法**：记下上次贴底时的 `contentSize.height`，没变就跳过。
- **风险**：低，但收益也小（`setContentOffset(animated: false)` 本身很便宜），优先级最低。

## 5. 实测方法（数据待采集）

本篇所有排序与「瓶颈」判断都来自复杂度分析，**没有填入任何未实测的性能数字**。真机采集方法沿用 `doc/02` 第 8 节，不在此重复，要点：

1. 不配 API Key 走 `MockProvider`，把脚本替换为约 3000 字、覆盖标题/段落/列表/代码块/表格的 Markdown；
2. Instruments 用 **Time Profiler**（看 `flush()` / `applyPatch` / `heightThatFits` / `render` 的主线程占比）+ **Core Animation / Hitches**（看掉帧次数与总时长）；必须真机，模拟器数据不具代表性；
3. 对照组：在 `flush()` 里加开关强制每帧全量重切块 + 跳过 `AttributedCache`，对比两组曲线。预期对照组每帧耗时随时间递增，增量版大致平稳。

采集完成后，用实测数据重排第 4 节的优先级，并把 4.1 的线性开销在长回复后段的实际占比填进来——那是验证「闸门是否真的关严」最直接的指标。
