# 04 工具调用

对应代码：`WBAppleIntelligence/Features/ToolCalling/ToolCallingViewModel.swift`、`WBAppleIntelligence/Features/ToolCalling/ToolCallingDemoView.swift`、`WBAppleIntelligence/AIKit/Tools/ToolCallingService.swift`、`WBAppleIntelligence/AIKit/Tools/EnterpriseTools.swift`、`WBAppleIntelligence/AIKit/Tools/MockEnterpriseBackend.swift`。

## 1. 场景与价值

`ToolCallingDemoView` 对应的场景来自 `DemoRoute.toolCalling`（`WBAppleIntelligence/App/DemoRoute.swift`）：「让模型调用库存、订单等内部系统接口，用自然语言完成原本要点五六个页面的查询。」员工想知道「ThinkPad 现在还有多少库存」，不再需要打开 ERP 系统、找到库存模块、按型号筛选、切换仓库标签页——一句自然语言问题，模型自己决定要不要查、查哪个接口、传什么参数。

这个能力和前三个 Demo 有本质区别：前三个 Demo 里模型只处理「你喂给它的文本」，工具调用把模型的能力边界扩展到「你允许它触达的数据」。这个扩展如果发生在云端，会立刻变成一个数据合规问题——库存数量、订单状态这类内部系统数据，一旦要喂给云端模型做推理，就构成了一次「业务数据出企业网络」的事件。

`DemoRoute.toolCalling.value` 把这一点说得很直接：「模型只拿到工具的返回值，业务数据的访问边界由你的代码控制，不需要把数据喂给云端模型。」拆开看，这句话包含两层保证：

1. **业务数据始终留在设备内。** `InventoryLookupTool.call(arguments:)`、`OrderStatusTool.call(arguments:)` 都是在设备本地执行的普通 Swift 方法（`WBAppleIntelligence/AIKit/Tools/EnterpriseTools.swift`），背后查询的 `MockEnterpriseBackend`（真实项目里换成 HTTP 客户端或本地数据库）也运行在设备上。整条链路里，库存表、订单表本身从来没有被序列化、上传到任何服务器。
2. **模型只看得到你的代码决定返回的内容。** 模型能拿到的所有「事实」都是 `call(arguments:)` 的返回值——一句总结性的字符串。它看不到 `MockEnterpriseBackend` 里除此之外的任何数据，也看不到查询逻辑本身。访问边界不是由模型的「自觉」决定的，而是由 `call` 方法里写了什么决定的：不想让模型知道某个仓库的库存，最简单的做法就是在 `call` 里不把它拼进返回字符串。

这是云端方案结构性做不到的一点：云端模型要「知道」库存数据，只有两条路——要么把数据当作提示词的一部分发过去（数据出设备），要么部署一个云端可访问的 function-calling 后端（架构复杂度和数据出境的合规问题依然存在，只是转移了一层）。端侧工具调用把这两条路都绕开了：工具和模型跑在同一台设备上，「谁能看到什么」完全是本地代码的控制流问题，不涉及任何网络边界。

## 2. `Tool` 协议

框架对 `Tool` 协议的定位（`swift symbolgraph-extract` 读出的文档原文）：

> A tool that a model can call to gather information at runtime or perform side effects... A tool includes a name and a description that the framework puts in the prompt to let the model decide when and how often to call your tool.

协议的关键要求（整理自符号表，逐条对应各自的声明片段，非逐字源码排版）：

```
protocol Tool: Sendable, SendableMetatype {
    associatedtype Arguments: ConvertibleFromGeneratedContent
    associatedtype Output: PromptRepresentable
    var name: String { get }
    var description: String { get }
    var parameters: GenerationSchema { get }
    var includesSchemaInInstructions: Bool { get }
    @concurrent func call(arguments: Arguments) async throws -> Output
}
```

逐个看这几条要求：

- **`Arguments: ConvertibleFromGeneratedContent`**：模型给工具传参数之前，必须先把它生成的内容解码成这个类型。实践上唯一现实的选择是让 `Arguments` 是一个 `@Generable` struct——`Generable` 本身遵循 `ConvertibleFromGeneratedContent`，而且只有 `@Generable` 类型才带有框架能用来约束模型输出的 `GenerationSchema`。**用 `String`、`Int`、`Double`、`Bool`、`Decimal` 这类基础类型直接当 `Arguments` 会编译失败**——这不是文档里一句空泛的警告，是实测出来的编译器行为。用一个最小复现样例验证：

  ```swift
  struct BadTool: Tool {
      typealias Arguments = String
      let name = "bad"
      let description = "test"
      func call(arguments: String) async throws -> String {
          return arguments
      }
  }
  ```

  用工程实际的 `swiftc` 参数（`-swift-version 5`，`arm64-apple-ios26.5-simulator` target）对这段代码做 `-typecheck`，编译器报错：

  ```
  error: type 'BadTool' does not conform to protocol 'Tool'
  error: unavailable property 'parameters' was used to satisfy a requirement of protocol 'Tool': 'Tool' that uses 'String' as 'Arguments' type is unsupported. Use '@Generable' struct instead.
  ```

  根因在协议扩展里：框架给 `parameters` 提供的默认实现被标注了 `@available(*, unavailable, message: "...")`，专门用来在 `Arguments` 不是 `Generable` 时把编译错误提前到「哪个要求没实现」这一步，而不是让模型在运行时收到一个没有 schema 的工具定义再报错。`InventoryQuery`、`OrderQuery`（`WBAppleIntelligence/AIKit/Tools/EnterpriseTools.swift`）都是 `@Generable struct`，走的是唯一支持的路径。
- **`Output: PromptRepresentable`**：工具执行完之后，返回值要能被塞回给模型继续推理。`String` 已经内置遵循 `PromptRepresentable`，本工程两个工具的 `Output` 都直接用 `String`（一句人类可读的总结，而不是原始结构化数据），这也是「模型只拿到你的代码返回的内容」这句话在类型层面的体现。
- **`name: String`**：工具的唯一标识，框架文档给的例子是 `"get_weather"`、`"toggleDarkMode"` 这类简短的驼峰名。
- **`description: String`**：框架把这段文字连同 `name`、`parameters` 一起注入到会话的 instructions 里（见下一条），是模型判断「什么时候该调用哪个工具」的唯一依据——这一点直接决定了第 6 节要讲的工具设计经验。
- **`parameters: GenerationSchema`**：工具参数的 schema。
- **`includesSchemaInInstructions: Bool`**：框架注释写明默认实现是 `true`：「If true, the model's name, description, and parameters schema will be injected into the instructions of sessions that leverage this tool. The default implementation is `true`」，只有模型已经被训练到「天生认识」这个工具时才值得考虑关掉。
- **`call(arguments:) async throws -> Output`**：真正执行工具逻辑的地方，标注了 `@concurrent`（第 5 节详细展开）。

**`name`、`includesSchemaInInstructions` 都有协议扩展提供的默认实现，`parameters` 在 `Self.Arguments: Generable` 成立时也有默认实现（直接由 `Arguments.generationSchema` 合成）**——这意味着写一个最小的 `Tool` 只需要实现 `description` 与 `call`。用一个比 `InventoryLookupTool` 更简化的例子验证这一点（同样通过实测确认可以编译并运行）：

```swift
struct MinimalTool: Tool {
    typealias Arguments = MyArgs2   // @Generable struct
    let description = "test minimal"
    func call(arguments: MyArgs2) async throws -> String {
        return arguments.x
    }
}
```

不写 `name` 时，默认实现落回类型名本身——实测 `MinimalTool().name` 等于 `"MinimalTool"`；`includesSchemaInInstructions` 实测为 `true`。`InventoryLookupTool`、`OrderStatusTool` 仍然显式声明了 `name`（`"queryInventory"`、`"queryOrderStatus"`），是因为工具名会被写进 instructions 直接展示给模型，用类型名兜底在真实项目里往往不够语义化（类型名可能是 `InventoryLookupTool`，而不是一个动词短语），显式声明能让这个名字保持可读、稳定，不随类型改名而改变。

## 3. 调度是自动的

`ToolCallingService.makeSession()`（`WBAppleIntelligence/AIKit/Tools/ToolCallingService.swift`）把两个工具一次性交给 session：

```swift
private static func makeSession() -> LanguageModelSession {
    LanguageModelSession(
        model: .default,
        tools: [InventoryLookupTool(), OrderStatusTool()],
        instructions: Prompts.toolCalling
    )
}
```

之后整条链路里，业务代码只调用了一次 `session.respond(to: question)`（`ToolCallingService.ask(_:)`），没有再写任何「先判断要不要调用工具、再决定调用哪个、再拼参数、再把结果塞回去问一遍」的调度代码。这不是省略，而是这套调度本身就是 `LanguageModelSession` 内部实现的一部分：模型在生成过程中决定要调用某个工具时，框架会解码出符合 `Arguments` schema 的参数、执行对应 `Tool` 的 `call(arguments:)`、把返回值转成 `Transcript.ToolOutput` 追加进对话记录，再把追加后的上下文喂回模型继续生成——如果模型认为还需要调用别的工具，这个过程会重复，直到模型给出最终回答。

框架文档里还有一句容易被忽略的补充：「Tools must conform to `Sendable` so the framework can run them concurrently. If the model needs to pass the output of one tool as the input to another, it executes back-to-back tool calls.」——工具调用不仅是自动的，还可能是**并发**的：如果一次生成里模型决定调用多个工具，框架不保证按顺序串行执行。这也是为什么 `Tool` 协议要求 `Sendable`、`call(arguments:)` 要标 `@concurrent`（见第 5 节）——业务代码完全不用关心「什么时候调、调几次、要不要并发」，但要对「这段代码可能被并发调用」这件事本身负责。

## 4. 可审计性

`ToolCallingService.ask(_:)` 用的是非流式的 `session.respond(to:)`，返回的 `LanguageModelSession.Response<String>` 除了最终 `content`，还带一个 `transcriptEntries: ArraySlice<Transcript.Entry>`（框架注释：「The list of transcript entries.」）——这次 `respond` 调用期间新增的全部会话记录，不只是最终回答本身。

`Transcript.Entry` 是一个枚举，除了 `.instructions`、`.prompt`、`.response`，专门为工具调用留了两个 case：

```
case toolCalls(Transcript.ToolCalls)
case toolOutput(Transcript.ToolOutput)
```

两者携带的信息完全不同（同样取自符号表）：

- **`.toolCalls`** 携带的 `Transcript.ToolCall` 只有 `toolName: String` 和 `arguments: GeneratedContent`——记录的是模型**决定调用什么、传了什么参数**，不包含工具执行之后的结果。
- **`.toolOutput`** 携带的 `Transcript.ToolOutput` 有 `toolName: String` 和 `segments: [Transcript.Segment]`——记录的是这次调用**返回给模型的实际内容**，同时保留了是哪个工具产生的。

`ToolCallingService.toolCalls(in:)` 选的是 `.toolOutput` 而不是 `.toolCalls`，完整实现：

```swift
private static func toolCalls(
    in entries: ArraySlice<Transcript.Entry>
) -> [ToolCallRecord] {
    entries.compactMap { entry in
        guard case .toolOutput(let output) = entry else { return nil }
        let text = output.segments
            .compactMap { segment -> String? in
                if case .text(let textSegment) = segment { return textSegment.content }
                return nil
            }
            .joined(separator: "\n")
        return ToolCallRecord(id: output.id, toolName: output.toolName, output: text)
    }
}
```

原因很直接：界面要展示的是「模型查了什么、拿回了什么内容」——这正是 `.toolOutput` 一条记录就能同时给出的两件事（`toolName` + 实际返回文本）。如果改用 `.toolCalls`，拿到的是模型传的参数（比如物料关键词、仓库代码），还得再手动把它和后续某条 `.toolOutput` 按顺序或 id 配对，才能拼出「调了谁、传了什么、拿回了什么」的完整画面——多了一步不必要的关联逻辑，`.toolOutput` 本身已经把「调了谁」和「结果是什么」放在同一条记录里了。

`ToolCallingDemoView.toolTrace` 把这份 `[ToolCallRecord]` 渲染成一个独立分组，工具名和输出内容分别展示。这个设计决定背后的产品诉求是：企业场景里「这个数字是模型编的还是真查出来的」必须是一个可以回答的问题，而不是一个黑箱——把调用轨迹单独列出来，等于让用户（或者审计这次交互记录的人）能直接核对回答里的数字和工具实际返回的内容是否一致。

## 5. 并发隔离的坑

本工程在 `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` 下，任何没有显式标注隔离域的类型、扩展成员，默认都会被推断成 `@MainActor`——这是为了让 SwiftUI 代码（绝大多数要跑在主线程）不用到处手写 `@MainActor`。但 `Tool.call(arguments:)` 这条协议要求本身标了 `@concurrent`（符号表里的完整签名是 `@concurrent func call(arguments: Self.Arguments) async throws -> Self.Output`），意味着这个方法可能在任意隔离域（很可能不是主线程）被并发调用，框架注释也直接写明：「This method may be invoked concurrently with itself or with other tools.」

这就产生了一个默认设置和协议要求互相冲突的地方：`call` 是 nonisolated 的，但如果它访问了一个「什么都没标注、跟着工程默认落到 `@MainActor`」的共享数据源，就是在一个非隔离的方法里同步访问一个主线程隔离的类型——这类跨隔离域访问，在本工程实际使用的 `SWIFT_VERSION = 5.0`（Swift 5 语言模式）下**只会产生一条警告，不会编译失败**。用一个最小复现样例验证：

```swift
// 故意不标 nonisolated：在这个工程的默认隔离设置下，这个 struct 会被隐式推断为 @MainActor。
struct MainActorBackend {
    static let shared = MainActorBackend()
    let value: Int = 42
}

nonisolated struct LeakyTool: Tool {
    typealias Arguments = MyArgs3
    let name = "leaky"
    let description = "test"
    func call(arguments: MyArgs3) async throws -> String {
        return "\(MainActorBackend.shared.value)"
    }
}
```

用工程实际的编译参数（`-swift-version 5`、`-default-isolation MainActor`）对这段代码做 `-typecheck`，结果是：

```
warning: main actor-isolated static property 'shared' cannot be accessed from outside of the actor; this is an error in the Swift 6 language mode
```

这条诊断信息本身写明了「这是 Swift 6 语言模式下的错误」，反过来说明在本工程实际使用的 Swift 5 模式下它只是警告——不会让 `xcodebuild` 失败，但会让 `warning: ` 的计数从 0 变成 1，直接违反本工程「clean build 零警告」的验收标准。这个坑不会在「代码能不能跑」这一层暴露出来，只会在「这次改动有没有引入新警告」这层检查里暴露——如果没有零警告的强约束，这类隔离标注遗漏很容易被放过去。

`MockEnterpriseBackend`（`WBAppleIntelligence/AIKit/Tools/MockEnterpriseBackend.swift`）就是需要显式标 `nonisolated` 的地方：

```swift
nonisolated struct MockEnterpriseBackend: Sendable {

    struct StockRecord: Equatable, Sendable {
        let item: String
        let warehouse: String
        let quantity: Int
    }

    struct OrderRecord: Equatable, Sendable {
        let orderID: String
        let status: String
        let expectedDelivery: String
    }

    static let shared = MockEnterpriseBackend()

    // ...
}
```

真正需要显式标注的是**共享数据源**（`MockEnterpriseBackend`）本身，而不是 `Tool`-遵循类型（`InventoryLookupTool`、`OrderStatusTool`）——后者即使不写 `nonisolated` 也能编译通过：SE-0466 允许编译器根据协议要求的隔离域（这里是 `call(arguments:)` 的 `@concurrent`/nonisolated）反推出满足该要求的见证方法应有的隔离域，一个空标注的 struct 只要它的见证方法能被推断为 nonisolated，就足以满足协议。实测验证：把 `InventoryLookupTool`、`OrderStatusTool` 的 `nonisolated` 去掉，在同样的 `-default-isolation MainActor` 参数下依然可以 typecheck 通过、零警告。本工程仍然在这两个 struct 上显式写了 `nonisolated`（`EnterpriseTools.swift` 的注释：「虽然 SE-0466 下 `@concurrent` 协议的见证会自动推断为 nonisolated，但显式标注有助于保持文件中隔离策略的可读性」），是可读性上的选择，不是编译上的必需——但 `MockEnterpriseBackend` 这类被 `call` 直接访问的共享状态，`nonisolated` 是必需的，漏掉就会退化成上面那条容易被忽略的警告。

## 6. 工具设计经验

三条经验都直接来自 `EnterpriseTools.swift`、`MockEnterpriseBackend.swift` 里已经写好的实现，这里把「为什么这么做」展开说清楚：

1. **`description` 要写清楚「什么情况下必须调用」，而不是泛泛描述工具做什么。** `InventoryLookupTool.description` 写的是：「查询指定物料在各仓库的实时库存数量。**需要具体库存数字时必须调用本工具。**」后半句「必须调用」是关键——`description` 是模型判断「这个问题该不该触发工具调用」的唯一依据（连同 `name` 一起被注入 instructions，见第 2 节）。如果只写「查询库存」这种平淡描述，模型在拿不准的情况下容易选择跳过工具、直接凭训练数据里的常识编一个看起来合理的数字，而不是意识到「这是一个必须查证的问题」。

2. **查不到时要返回一句明确的说明，不能返回空字符串。** `InventoryLookupTool.call(arguments:)` 里的处理：

   ```swift
   // 查不到时返回明确说明而不是空串：空串会让模型以为工具没生效，
   // 转而凭记忆编一个数字出来。
   guard !records.isEmpty else {
       let scope = arguments.warehouse.map { "仓库 \($0)" } ?? "所有仓库"
       return "未查询到「\(arguments.item)」在\(scope)的库存记录。"
   }
   ```

   `OrderStatusTool` 是同样的处理：查不到订单时返回「未查询到订单 \(arguments.orderID)。请核对订单号是否正确。」而不是抛错或返回空串。原因是模型看到的只是 `Output` 这一个字符串，它没有办法区分「工具正常执行、只是数据里确实没这条记录」和「工具没有正常返回任何东西」——如果返回空串，两种情况在模型眼里长得一样，模型很可能选择继续用自己的语言模型知识把这个问题「填」上，结果是编出一个订单状态。返回一句明确的「未查询到」，等于把「查不到」也变成一个工具能正常表达的结果，模型才能如实转述而不是编造。

3. **用模糊匹配而不是精确匹配。** `MockEnterpriseBackend.stock(forItem:warehouse:)` 用的是 `localizedCaseInsensitiveContains`，而不是精确相等：

   ```swift
   // 用模糊匹配是刻意的：模型从用户口语里提取出的物料名往往不完整
   // （「联想那个笔记本」→「ThinkPad」），精确匹配会大面积查不到。
   func stock(forItem item: String, warehouse: String?) -> [StockRecord] {
       stockRecords.filter { record in
           guard record.item.localizedCaseInsensitiveContains(item) else { return false }
           guard let warehouse else { return true }
           return record.warehouse.caseInsensitiveCompare(warehouse) == .orderedSame
       }
   }
   ```

   模型从员工口语里抽取出的关键词，本身就是一次「理解 + 压缩」，不会逐字保留数据库里的完整型号名（数据库里是「ThinkPad X1 Carbon」，员工可能只说「ThinkPad」或者「那个笔记本」）。工具如果坚持做精确匹配，会把这种正常的信息损失当成「查不到」处理，而这类误判在用户体验上和「模型真的编了个假数字」是同样糟糕的结果——用户分不清是数据里真没有，还是查询逻辑本身太死板。仓库代码字段（`SH01`/`BJ02`）保留了精确匹配（`caseInsensitiveCompare(_:) == .orderedSame`），因为仓库代码本身是一个封闭、简短的枚举值集合，模型抽取出错的概率远低于自由文本物料名。

## 7. 错误处理

框架提供的 `LanguageModelSession.ToolCallError` 是专门包装「工具内部执行失败」这种错误的类型，完整结构（取自符号表）：

```
struct ToolCallError: LocalizedError {
    var tool: any Tool
    var underlyingError: any Error
    init(tool: any Tool, underlyingError: any Error)
}
```

框架对 `call(arguments:)` 的文档写明了这个类型的用途：「If errors are thrown in the body of this method, they will be wrapped in a `LanguageModelSession.ToolCallError` and rethrown at the call site of `respond(to:options:)`.」也就是说，如果 `InventoryLookupTool.call(arguments:)` 或 `OrderStatusTool.call(arguments:)` 内部 `throw` 了什么错误，业务代码不会直接拿到那个原始错误，而是拿到一个 `ToolCallError`，其中 `tool` 告诉你是哪个工具出的问题，`underlyingError` 是工具内部真正抛出的那个错误。

**本 Demo 里这条路径目前不会被触发**：`InventoryLookupTool` 和 `OrderStatusTool` 的 `call` 实现里都没有任何 `throw` 语句（第 6 节讲的「查不到就返回一句说明」，走的是正常返回值，不是抛错），所以 `ToolCallError` 在这两个工具当前的实现下永远不会被产生。这里如实记录这一点，而不是假装已经测试过一条实际上从未被执行到的错误路径。

如果未来某个工具确实需要抛错（比如后端调用超时、鉴权失败这类真正的异常，而不是「查不到」这种正常业务结果），要注意一个现状：`AIKitError.init(_:)`（`WBAppleIntelligence/AIKit/Core/AIKitError.swift`）目前只对 `LanguageModelSession.GenerationError` 做了逐 case 映射，其余错误类型（包括 `ToolCallError`）会落进兜底分支：

```swift
guard let generation = error as? LanguageModelSession.GenerationError else {
    self = .underlying(error.localizedDescription)
    return
}
```

也就是说 `ToolCallError` 会被 `AIKitError(_:)` 统一处理成 `.underlying(error.localizedDescription)`——`tool`、`underlyingError` 这两个字段携带的结构化信息（哪个工具、什么原因）会被压缩成一句 `localizedDescription` 文本，界面上仍然能看到一条错误提示（`ErrorView` 照常渲染），只是丢失了「具体是哪个工具出的问题」这种可以单独判断、单独处理的结构化信息。这是当前实现的一个已知取舍，不是需要立刻修的 bug——因为这条路径在这两个工具的当前实现里根本不会被触发，但如果后续给工具加上真正会失败的调用（网络请求、数据库访问），这里是需要回头补一个 `ToolCallError` 专属 case 的地方。

## 8. 踩坑记录

- **`@Guide(.pattern(...))` 的正则字面量必须写 `#/.../#`。** `Docs/03-结构化生成.md` 第 3 节已经用最小复现样例验证过这个结论（裸斜杠 `/.../` 在 `.pattern(` 后面会被编译器当成前缀一元运算符去解析）。这个结论在本 Demo 里第一次真正被用到：`OrderQuery.orderID` 需要约束订单号必须形如 `SO-2026-0417`，实际写法是

  ```swift
  @Guide(description: "销售订单号，形如 SO-2026-0417", .pattern(#/SO-\d{4}-\d{4}/#))
  var orderID: String
  ```

  用 `#/.../#` 而不是裸斜杠，是本工程 `SWIFT_VERSION = 5.0` 下的硬性要求，不是风格偏好。

- **忘记给共享数据源标 `nonisolated`，在 Swift 5 语言模式下只是一条警告，不是编译错误。** 详见第 5 节的实测：`Tool.call(arguments:)` 是 nonisolated 的协议要求，如果它访问的共享状态跟着工程默认落到 `@MainActor`，在本工程实际使用的 Swift 5 语言模式下只会产生一条「在 Swift 6 模式下会是错误」的警告，代码依然能跑。这类问题不会在「build 失败」这一层暴露出来，只会在「有没有新增警告」这层检查里暴露——本工程把「clean build 零警告」当作硬性验收标准，就是为了让这类本该显式处理、但语言层面允许悄悄溜过去的隔离遗漏，能被尽早捕捉到。

## 9. 性能数据

`ToolCallingService.ask(_:)` 用 `MetricsTimer`、`SystemLanguageModel.default.tokenCount(for:)` 采集指标的机制，和前两个 Demo 是同一套（见 `Docs/02-流式对话与会话管理.md` 第 6 节），但工具调用场景下这些数字的构成更复杂：一次 `respond(to:)` 背后可能包含「模型决定调用工具 → 框架执行 `call` → 结果回灌给模型 → 模型继续生成」好几轮来回，`GenerationMetrics.totalDuration` 度量的是这一整条链路的总耗时，不仅仅是「模型生成文字」那一段——工具本身的执行时间（本 Demo 里是内存查询，量级可以忽略；真实项目里如果工具背后是网络请求，这段时间会被算进同一个 `totalDuration` 里）。

> **待真机实测**：工具调用场景下的首字延迟、总耗时，以及它们与「这次提问触发了几次工具调用」之间的关系。测试方法：在已开启 Apple Intelligence 的 iPhone 15 Pro 及以上机型上，依次测试 `ToolCallingViewModel.samples` 里的三个预置问题（命中库存、按仓库过滤、查订单状态）与一个查不到的订单号，记录 `MetricsBar` 展示出的「首字」「总耗时」（对应 `GenerationMetrics.firstTokenLatency`、`totalDuration`）与「输入/输出」token 数，并与 `Docs/02-流式对话与会话管理.md` 记录的不带工具的普通对话耗时做对比，观察多一轮工具调用相比纯文本生成，耗时具体增加了多少。
