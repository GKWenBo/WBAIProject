# 01 可用性探测与降级

对应代码：`WBAppleIntelligence/Features/Availability/AvailabilityDemoView.swift`、`WBAppleIntelligence/AIKit/Core/ModelAvailability.swift`、`WBAppleIntelligence/App/RootView.swift`。

## 1. 场景与价值

企业 App 接入端侧模型，第一件要做的事不是「怎么生成」，而是「能不能生成」。`SystemLanguageModel` 依赖的 Apple Intelligence 在设备之间的分布并不均匀：

- 机型是否达标（例如 iPhone 15 Pro 及以上）；
- 系统版本是否够新；
- 设备区域 / 系统语言是否落在 Apple Intelligence 的支持范围内；
- 用户是否在系统设置里手动开启过开关；
- 模型资源是否已经下载完成。

以上任意一环不满足，`availability` 都会变成 `unavailable`，而且原因各不相同、对应的用户引导也完全不同。如果把「有 AI 功能」这件事写死在代码里（例如用编译期宏或者一次性判断），线上必然会出现「按钮点了没反应」「崩溃」或者「静默失败」——这些问题对企业客户来说都是实打实的工单。

所以「探测 + 降级」不是一个锦上添花的收尾步骤，而是端侧 AI 功能的地基：先确定当前设备处于哪种状态，再决定是走 AI 路径、走传统路径，还是引导用户去开启开关。本 Demo（`AvailabilityDemoView`）刻意不包含任何生成逻辑，只做探测和展示，就是为了把这一步单独隔离出来，作为后面三个 Demo 的公共前提。

## 2. API 讲解

`AvailabilityDemoView` 直接持有一个 `SystemLanguageModel` 实例：

```swift
private let model = SystemLanguageModel.default
```

`SystemLanguageModel.default` 是系统提供的默认单例，对应 `UseCase.general`（见下文）。围绕它，本 Demo 用到了以下 API：

- **`availability: SystemLanguageModel.Availability`**：当前可用性状态，`.available` 或 `.unavailable(UnavailableReason)`。这是判断「能不能用」的唯一权威来源。
- **`isAvailable: Bool`**：`availability == .available` 的语法糖，`ModelAvailability` 里同名属性就是照这个语义实现的。
- **`supportedLanguages: Set<Locale.Language>`**：模型支持的语言集合。注意这与 `availability` 是两件独立的事——即使模型可用，用户当前语言也可能不在这个集合里。
- **`supportsLocale(_ locale: Locale = .current) -> Bool`**：判断某个 `Locale`（默认当前系统 `Locale`）是否被模型支持，本质上是对 `supportedLanguages` 的一层封装判断。
- **`contextSize: Int`**：模型单次会话支持的最大 token 数，包含输入提示词与生成内容的总和。这是框架报告的固定常量，**值为 4096**，与机型、系统版本无关。
- **`SystemLanguageModel(useCase: UseCase = .general, guardrails: Guardrails = .default)`**：如果不想用默认单例，可以按用途构造独立实例。

关于 `UseCase`，框架文档原文（通过 `swift symbolgraph-extract` 从 `FoundationModels.framework` 的符号表中读取）分别是：

- `UseCase.general`：*"A use case for general prompting. This is the default use case for the base version of the model, so if you use `SystemLanguageModel/default`, you don't need to specify a use case."* —— 即通用对话/生成场景，`SystemLanguageModel.default` 内部用的就是它，不需要手动指定。
- `UseCase.contentTagging`：*"A use case for content tagging. Content tagging produces a list of categorizing tags based on the input prompt. When specializing the model for the `contentTagging` use case, it always responds with tags."* —— 专门做内容打标签（分类/情绪/动作/物体识别），模型会被特化为「只吐标签」的行为，不适合拿来做普通对话。

两者的区别不是「能力多寡」，而是「模型被特化的输出形态」：`.general` 面向自由文本/结构化生成，`.contentTagging` 面向固定形态的标签列表。本工程后续三个 Demo（流式客服、工单抽取、工具调用）都属于 `.general` 场景，因此全部使用 `SystemLanguageModel.default`，没有单独构造 `.contentTagging` 实例。

## 3. 三种不可用原因

`SystemLanguageModel.Availability.UnavailableReason` 有三个 case，`ModelAvailability` 把它们分别翻译成用户可读的标题、说明与操作建议。三者的真实成因（同样取自框架符号表里的文档注释）与对应文案如下：

- **`deviceNotEligible`** —— 官方注释：*"The device does not support Apple Intelligence."* 即机型不满足要求，或者更隐蔽的一种情况：**设备区域 / 系统语言不在 Apple Intelligence 支持范围内**，即使硬件完全达标也会落在这个 case 里（详见第 5 节的实测记录）。
- **`appleIntelligenceNotEnabled`** —— 官方注释：*"Apple Intelligence is not enabled on the system."* 机型和区域都满足，但用户还没有在系统设置里手动打开 Apple Intelligence 开关。
- **`modelNotReady`** —— 官方注释：*"The model(s) aren't available on the user's device. Models are downloaded automatically based on factors like network status, battery level, and system load."* 开关已经打开，但模型文件仍在下载或准备中，下载时机由系统根据网络状况、电量、系统负载自动决定，App 无法主动触发或加速。

`ModelAvailability.Reason` 里对应的实现（`WBAppleIntelligence/AIKit/Core/ModelAvailability.swift`）：

```swift
nonisolated extension ModelAvailability.Reason {
    var title: String {
        switch self {
        case .deviceNotEligible: "此设备不支持端侧模型"
        case .appleIntelligenceNotEnabled: "尚未开启 Apple Intelligence"
        case .modelNotReady: "模型尚未就绪"
        case .unknown: "端侧模型当前不可用"
        }
    }

    var detail: String {
        switch self {
        case .deviceNotEligible:
            "需要 iPhone 15 Pro 及以上机型，且设备区域与系统语言需在 Apple Intelligence 支持范围内。中国大陆区域目前不在支持范围内。"
        case .appleIntelligenceNotEnabled:
            "设备支持端侧模型，但用户还没有在系统设置里打开 Apple Intelligence 开关。"
        case .modelNotReady:
            "开关已打开，但模型文件仍在下载或正在准备中。模型体积以 GB 计，首次启用需要时间与网络。"
        case .unknown:
            "系统返回了当前 App 尚未识别的不可用原因，可能来自更高版本的系统。"
        }
    }

    /// 给用户的下一步操作建议。企业 App 里这段文案直接决定了工单量。
    var recovery: String {
        switch self {
        case .deviceNotEligible:
            "请在支持的机型上使用，或继续使用不依赖端侧模型的常规功能。"
        case .appleIntelligenceNotEnabled:
            "请前往「设置 → Apple 智能与 Siri」开启 Apple Intelligence。"
        case .modelNotReady:
            "请保持网络连接并接入电源，稍后重试。"
        case .unknown:
            "请稍后重试；若持续出现，请升级 App 到最新版本。"
        }
    }
}
```

三段文案的分工很明确：`title` 用于横幅标题，`detail` 解释成因（给用户和给排查问题的人看），`recovery` 是唯一一条「用户接下来该做什么」——这条文案直接决定了用户是自助解决还是提工单。

## 4. Observable 驱动的自动恢复

`SystemLanguageModel` 遵循 `Observation.Observable`（可通过 `swift symbolgraph-extract` 导出的符号关系表确认：`SystemLanguageModel conformsTo Observation.Observable`）。这意味着只要在 SwiftUI 的 `body` 里读取它的 `availability`，SwiftUI 就会自动追踪这次读取；用户之后在系统设置里切换 Apple Intelligence 开关时，View 会自动重新求值，界面上的横幅、能力列表会跟着刷新——不需要自己监听通知、也不需要下拉刷新或重启 App。

首页 `RootView` 就是这样用的（`WBAppleIntelligence/App/RootView.swift`）：

```swift
struct RootView: View {
    private let model = SystemLanguageModel.default

    var body: some View {
        NavigationStack {
            List {
                Section {
                    AvailabilityBanner(availability: ModelAvailability(model.availability))
                        .listRowInsets(EdgeInsets(top: 8, leading: 16, bottom: 8, trailing: 16))
                }
                // ...
            }
            .navigationTitle("端侧 AI 能力")
            .navigationDestination(for: DemoRoute.self) { destination(for: $0) }
        }
    }
    // ...
}
```

关键点是 `model.availability` 是在 `body` 内部被访问的，而不是缓存成一个存储属性在 `init` 里算好——后者会导致这个值只在 View 创建时计算一次，用户后续切换开关也不会触发刷新。`AvailabilityDemoView` 采用了同样的写法（在 `body` 里 `let availability = ModelAvailability(model.availability)`），保证每次 View 重新求值时都拿到最新状态。

## 5. 踩坑记录

以下三条是这个工程在开发过程中的真实实测结论：

1. **开发机区域为 `zh_CN` 时，`availability` 会返回 `unavailable`，即使硬件是 Apple M4 Pro。** 在本机（`Mac mini`，芯片 `Apple M4 Pro`）上通过命令行直接调用框架验证：

   ```
   printf 'import FoundationModels\nprint(SystemLanguageModel.default.availability)\n' | xcrun swift -
   ```

   本次（Task 6）实测输出：

   ```
   unavailable(FoundationModels.SystemLanguageModel.Availability.UnavailableReason.deviceNotEligible)
   ```

   可靠的结论是：在 `zh_CN` 区域，`availability` 会返回 `unavailable`，且设备区域确实是 Apple Intelligence 官方文档写明的资格判定因素之一（见第 3 节 `deviceNotEligible` 的框架注释，以及 `ModelAvailability.Reason.deviceNotEligible` 的 `detail` 文案里「中国大陆区域目前不在支持范围内」这句）。但具体落在哪一个 `UnavailableReason` case 上，并不是一个只由「区域」这一个变量决定的确定性结果——Task 5 在同一台机器上曾测得的原因是 `appleIntelligenceNotEnabled`（见 `task-5-report.md`），而本次任务在同一台机器上测得的是 `deviceNotEligible`。**推测最可能的解释是宿主 Mac 的 Apple Intelligence 开关状态在两次测试之间发生了变化**——这只是推测，本项目没有做过控制变量的实验去坐实它，但它比其他解释更简单：开关本身就可以被系统或用户随时切换，两次观测之间也确实隔了一段时间、经历了不同的操作。

2. **iOS 模拟器的 Foundation Models 走宿主 Mac 的模型。** 在 iOS Simulator 里运行本工程、进入「端侧可用性探测」页时，App 报告的可用性状态实际来自宿主 Mac 当前的 Apple Intelligence 状态，而不是模拟器本身模拟出的某种设备状态。这意味着：在模拟器里改变可用性表现（从不可用变为可用、或切换不可用原因）的唯一方式是去改宿主 Mac 系统设置里的 Apple Intelligence 开关，模拟器内部没有独立的开关。

   本次任务测试期间还观察到一个现象：命令行一次性查询（见上面第 1 条）拿到的是 `deviceNotEligible`，而 App 内读取到的是 `appleIntelligenceNotEnabled`，两次读数的具体原因不一致。**推测最可能的原因同样是宿主 Mac 的 Apple Intelligence 开关状态在这段测试过程中发生了变化**，而不是命令行环境与 App 内环境本质不同——这一点尚未验证，只是这个解释比其他假设更简单，也和 Task 5 单独测得 `appleIntelligenceNotEnabled` 的记录能对上。

   这里要特别澄清一个容易被混为一谈、但其实**不相关**的机制：这个工程目前没有声明中文本地化资源（没有 `zh-Hans.lproj`），所以 `Locale.current.identifier` 在 App 内会协商出 `en_CN`，而不是系统实际设置的 `zh_CN`——`AvailabilityDemoView` 「模型能力」分组里「当前地区标识」这一行显示的就是这个协商结果（协商机制与 `AppleLanguages`/`developmentRegion` 的排查过程见 `task-5-report.md` 的「顾虑」部分）。**但这解释的只是 `Locale.current` 这个显示值，是一套独立于 `SystemLanguageModel` 资格判定的机制**：本项目没有任何实验证明 `SystemLanguageModel.availability` 的判定会依赖调用方 App 协商出的 `Locale.current`。把「App 缺少本地化资源」当成上面 `deviceNotEligible`/`appleIntelligenceNotEnabled` 原因不一致的成因，是把两件独立的事混为一谈，本文档不再这样归因。

3. **不需要写一个完整 App 就能查可用性状态。** 只要装了对应版本的 Xcode / 命令行工具，一行命令就能验证当前宿主环境的 Apple Intelligence 状态，适合在开始写 UI 之前先确认环境：

   ```
   printf 'import FoundationModels\nprint(SystemLanguageModel.default.availability)\n' | xcrun swift -
   ```

   这个方法在联调「为什么模拟器里横幅总是橙色」这类问题时特别有用——可以先排除是不是宿主环境本身就不可用，再去看 App 代码。

## 6. 限制与降级

`availability == .available` 只回答了「模型这个组件本身能不能跑」，它不等于「接下来的每一次调用都会成功」。至少还有两道独立的关卡：

- **语言 / 地区关卡**：`supportedLanguages` 与 `availability`是两件独立的事。即使 `availability` 是 `.available`，用户的系统语言也可能不在 `supportedLanguages` 里；这种情况下发起生成请求会抛出 `LanguageModelSession.GenerationError.unsupportedLanguageOrLocale`（工程里映射成 `AIKitError.unsupportedLanguage`，见 `AIKit/Core/AIKitError.swift`）。`supportsLocale(_:)` 就是用来提前判断这道关的。
- **运行时关卡**：即使可用性和语言都通过，单次调用仍可能因为上下文超限、护栏拦截、限流、并发冲突等原因失败——这些属于生成阶段的错误，不在本文档范围内（见后续 Demo 文档）。

基于这两道关卡，实际项目里通常有三种降级策略，各有取舍：

1. **走传统规则引擎 / 本地逻辑**：不可用时用关键词匹配、模板、状态机等非 AI 手段兜底。优点是行为可预测、不依赖网络也不依赖模型下载，适合工单分类、简单问答这类有明确规则的场景；缺点是覆盖面和语言理解能力远不如模型，维护规则本身也有成本。
2. **走云端模型**：不可用时转调云端 API。优点是不受端侧机型/区域限制，能力上限更高；缺点是引入网络依赖、延迟、token 费用，以及数据出设备/出境的合规问题——这恰恰是很多企业选择端侧方案的初衷，所以这条路径要谨慎，通常只用于对隐私不敏感的场景。
3. **直接隐藏入口**：不可用时不展示 AI 功能入口。优点是实现最简单，不会让用户看到「点了没反应」；缺点是用户完全不知道这个能力存在，也没有任何引导路径去开启它（比如提示去设置里打开开关）。适合这个功能是「锦上添花」而非核心流程的场景。

`AvailabilityBanner` 选择的是第 3 种的变体：不隐藏入口，而是把原因和下一步操作讲清楚，本质上是让用户自己有机会走到「开启开关」这条恢复路径上，而不是被沉默地拒之门外。三种策略不是互斥的：现实项目里往往是「优先端侧 → 端侧不可用降级到规则引擎 → 关键路径可选云端兜底」的组合，具体选哪几层取决于功能的核心程度和数据敏感度。

## 7. 非 frozen 枚举与 `@unknown default`

通过 `swift symbolgraph-extract` 导出 `FoundationModels` 的公开符号可以确认：`SystemLanguageModel.Availability` 本身标注了 `@frozen`，但它内部的 `UnavailableReason` 没有这个标注，也就是说 `Availability` 这个外层枚举的形状（`.available` / `.unavailable`）是稳定的，但 `UnavailableReason` 的 case 列表可能在未来的系统版本里新增。

这正是 `ModelAvailability.init(_:)` 里要写 `@unknown default` 分支的原因：

```swift
init(_ availability: SystemLanguageModel.Availability) {
    switch availability {
    case .available:
        self = .available
    case .unavailable(let reason):
        switch reason {
        case .deviceNotEligible:
            self = .unavailable(.deviceNotEligible)
        case .appleIntelligenceNotEnabled:
            self = .unavailable(.appleIntelligenceNotEnabled)
        case .modelNotReady:
            self = .unavailable(.modelNotReady)
        @unknown default:
            self = .unavailable(.unknown)
        }
    }
}
```

如果不写这个分支，代码在今天能编译通过、能跑；但一旦用户升级到某个新增了 `UnavailableReason` case 的系统版本，`switch` 会因为缺少覆盖而在编译期报错（如果不加 `@unknown default`，Swift 编译器会强制要求穷举所有已知 case，新增 case 会直接导致这份源码在新 SDK 下编译失败），或者——如果当初为了图省事用了 `default:` 兜底所有分支——会把新 case 的信息直接丢弃，用户拿到一个语焉不详的「不可用」提示，问题原因和对应的解决建议都对不上。

集中在 `ModelAvailability` 这一层加 `@unknown default` 并映射到自定义的 `.unknown` case，好处是把「系统给了个没见过的原因」这件事变成一个可以正常展示、正常测试的普通分支（`Reason.unknown` 同样有 `title` / `detail` / `recovery` 三段文案），而不是让编译错误传播到每一个用到 `ModelAvailability` 的地方，也不是在运行时默默丢信息。这是处理任何非 frozen 系统枚举的标准做法：入口处一次性兜底，业务代码就不用关心「万一系统又加了新 case」这种问题。
