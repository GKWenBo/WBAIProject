# 02 流式对话与会话管理

对应代码：`WBAppleIntelligence/Features/Chat/ChatViewModel.swift`、`WBAppleIntelligence/Features/Chat/ChatDemoView.swift`、`WBAppleIntelligence/AIKit/Chat/StreamingChatService.swift`、`WBAppleIntelligence/AIKit/Core/TranscriptTrimmer.swift`、`WBAppleIntelligence/AIKit/Core/GenerationMetrics.swift`。

## 1. 场景与价值

`ChatDemoView` 对应的场景是企业内部 IT 服务台的知识客服：员工用自然语言描述遇到的问题（网络、账号、设备……），端侧模型逐字流式给出解答，`Prompts.helpdesk` 里定义的角色设定和回答规则约束了它的语气与边界（见 `WBAppleIntelligence/AIKit/Core/Prompts.swift`）。

相比接一个云端大模型客服，端侧方案在企业场景里对应三个具体诉求：

- **对话内容不出设备，满足数据不出境与内部资料保密要求。** 员工问的问题里经常夹带内部系统名称、报错信息、甚至截图里的账号——这些内容如果要发到云端做一次问答，就构成了一次「内部数据出企业网络」的事件，很多行业（金融、政务、涉密单位）的合规要求会直接卡死这条路径，或者要求走复杂的审批与脱敏流程。端侧推理把这个问题从「怎么脱敏 / 怎么审批」变成「不存在」——数据从来没有离开过这台设备。
- **无 token 费用。** 云端方案是按 token 计费的，客服场景又恰好是高频、长尾的场景（一个员工可能一天问好几次网络配置），云端方案的账单会随员工规模线性增长。端侧模型的计算成本已经摊在硬件里，多问一次不产生边际费用，这对要把 AI 客服铺给全体员工的企业来说是能不能大规模推广的关键变量。
- **断网可用。** 员工的网络问题本身就可能是「连不上公司 Wi-Fi」——如果客服机器人也要联网才能回答，恰恰在最需要它的时候失效。端侧模型的整条推理链路（`SystemLanguageModel` → `LanguageModelSession` → `streamResponse`）不依赖网络，这个场景下断网可用不是锦上添花，而是场景本身要求的能力。

这三点也是 `DemoRoute.streamingChat.value` 里写的文案（`WBAppleIntelligence/App/DemoRoute.swift`）：「对话内容不出设备，天然满足数据不出境与内部资料保密要求；无 token 费用，无网络延迟。」

## 2. 流式 API

流式回答的核心调用在 `StreamingChatService.streamOnce(_:options:onPartial:)`（`WBAppleIntelligence/AIKit/Chat/StreamingChatService.swift`）：

```swift
private func streamOnce(
    _ prompt: String,
    options: GenerationOptions,
    onPartial: (String) -> Void
) async throws -> (text: String, metrics: GenerationMetrics) {
    var timer = MetricsTimer()
    var latest = ""

    for try await snapshot in session.streamResponse(to: prompt, options: options) {
        timer.markFirstToken()
        latest = snapshot.content
        onPartial(latest)
    }

    guard !latest.isEmpty else { throw AIKitError.emptyResponse }
    // ...
}
```

`session.streamResponse(to:options:)` 返回的是 `LanguageModelSession.ResponseStream<String>`，一个异步序列，`for try await snapshot in stream` 每次迭代拿到一个 `Snapshot`。

**这里有一个必须写清楚的细节，也是这份文档里最容易踩的坑：`snapshot.content` 是从生成开始累计到当前时刻的完整文本，不是这一次增量新增的那几个字符。** 换句话说，第一次迭代 `snapshot.content` 可能是「您」，第二次是「您好」，第三次是「您好，请」……每一次拿到的都是「从头到现在」的全部内容。所以上面代码里 `latest = snapshot.content` 是唯一正确的写法：直接整体赋值，用最新的快照替换掉上一次的内容。

如果反过来把它当成增量、写成 `latest += snapshot.content` 那样的拼接，结果会是「您」+「您好」+「您好，请」……重复内容一层层往上叠，界面上会看到文字疯狂重复而不是流畅地逐字出现。`ChatViewModel.send()` 里的 `onPartial` 闭包同样是直接赋值：

```swift
let outcome = try await service.respond(
    to: prompt,
    options: GenerationOptions(temperature: temperature)
) { partial in
    messages[replyIndex].text = partial
}
```

`messages[replyIndex].text = partial` 每次都用最新快照整体覆盖，这一条消息在界面上就呈现出「逐字增长」的效果，而背后的数据流是不断被替换而不是被拼接的。

## 3. `prewarm()`

`SystemLanguageModel` 支持的会话首次响应包含一次「冷启动」代价——模型权重要被载入内存，这段时间会直接叠加到用户感知到的首字延迟上。`prewarm()`（`LanguageModelSession.prewarm(promptPrefix:)`）的作用就是把这段加载提前到用户还没有真正发起请求的时候去做。框架文档原文（`swift symbolgraph-extract` 读出的注释）说明了它的适用场景和限制：

> This method can be useful in cases where you have a strong signal that the user will interact with session within a few seconds. For example, you might call prewarm when the user begins typing into a text field.
>
> Important: You should only use prewarm when you have a window of at least 1 second before the call to a respond method... Calling this method does not guarantee that the system loads your assets immediately, particularly if your app is running in the background or the system is under load.

`StreamingChatService.prewarm()` 就是对这个方法的直接转发，`ChatDemoView` 在 `.task` 里调用它：

```swift
.task {
    // 用户已经进到对话界面了，这时预热的收益最大、浪费最小。
    viewModel.prewarm()
}
```

调用时机是刻意选择的取舍：**在用户进入对话界面时调用，而不是在 App 启动时调用。** 原因是预热的代价是内存占用——模型权重被提前载入内存后会一直占着，直到会话结束或被系统回收。如果放在 App 启动时机，意味着哪怕用户这次打开 App 根本不打算用对话功能（比如只是来看看工单历史），也要背上这份内存开销；而放在用户已经点开对话页这个时间点，意味着预热几乎总能换来收益——用户大概率紧接着就会开始打字提问，这与框架文档「a strong signal that the user will interact with session within a few seconds」的建议场景完全吻合。

> **待真机实测**：预热前后的首字延迟对比。测试方法：在真机上分别测「不调用 `prewarm()`，进入对话页后立刻发送第一条消息」与「进入对话页后等待若干秒（确保预热已完成）再发送第一条消息」两种路径下，从发送到 `MetricsTimer.markFirstToken()` 记录到首个增量之间的耗时（即 `GenerationMetrics.firstTokenLatency`），对比两组数字得出预热的实际收益。

## 4. `GenerationOptions`

`GenerationOptions` 是控制模型如何从概率分布里选词的参数集合，`ChatViewModel.send()` 目前只暴露了其中一个给用户调：

```swift
let outcome = try await service.respond(
    to: prompt,
    options: GenerationOptions(temperature: temperature)
) { ... }
```

框架里与采样相关的几个成员：

- **`temperature: Double?`**——框架注释：「Temperature is an adjustment applied to the probability distribution prior to sampling. A value of `1` results in no adjustment. Values less than `1` will make the probability distribution sharper... low temperatures manifest as more stable and predictable responses, while high temperatures give the model more creative license.」取值范围 `0...1`。这正是 `ChatDemoView.temperatureSlider` 把滑杆范围钉死在 `0...1` 的原因——温度调到 0 时回答更稳定、更接近「每次都选最可能的词」，调到 1 时更发散，这个滑杆存在的目的就是让人在同一个 Demo 里直观看到两者的差别。
- **`maximumResponseTokens: Int?`**——框架注释：「If the model produce `maximumResponseTokens` before it naturally completes its response, the response will be terminated early. No error will be thrown... If no value is specified, then the model is allowed to produce the longest answer its context size supports.」本 Demo 没有设置这个值，回答长度只受 4096 token 的上下文窗口约束（见第 5 节）。
- **`sampling: SamplingMode?`**——本 Demo 留空，让系统选默认策略。框架提供了三种具体模式：
  - **`.greedy`**——「A sampling mode that always chooses the most likely token... Using this mode will always result in the same output for a given input.」永远选概率最高的词，输出最稳定但可能显得机械。
  - **`.random(top: Int, seed: UInt64?)`**——即 top-k 采样，只在概率最高的 k 个候选词里随机选。k 越小越接近 `.greedy`，越大越有创造性。
  - **`.random(probabilityThreshold: Double, seed: UInt64?)`**——即 top-p / nucleus 采样，候选池由「累计概率超过阈值」动态决定，而不是固定数量的词。

**`seed` 参数的意义在于让生成过程可以被大致复现，这对回归测试很重要**——比如给同一个提示词跑一遍自动化测试，如果每次输出都完全随机，测试就没法断言具体内容，只能退化成断言「有输出、没崩溃」这种弱校验。但框架的注释同时明确写了一句必须如实转述的限定：「Setting a random seed is not guaranteed to result in fully deterministic output. It is best effort.」——也就是说 `seed` 只是让结果「更可能一致」，不是数学意义上的确定性保证，写回归测试时不能假设两次调用会逐字节相同，只能用于「大体一致 / 不应该完全跑偏」这类模糊断言，或者配合 `.greedy` 一起使用来逼近可复现性。

## 5. 上下文窗口管理

端侧模型的上下文窗口是一个硬限制，框架的 `contextSize` 属性把这个值报告为 **4096**，注释写明「The context size represents the total number of tokens that can be used in a single session, including both input prompts and generated responses.」——instructions、历史对话、当前提示词、生成内容全部算在这 4096 个 token 里，会话越长，留给新一轮回答的空间就越少。

超限时框架抛出的错误是 `LanguageModelSession.GenerationError.exceededContextWindowSize`，框架注释给出的恢复建议是「Start new session when you exceed the content window size, and try again using a shorter prompt or shorter output length.」`StreamingChatService.respond(to:options:onPartial:)` 就是照着这个建议实现的自动恢复：

```swift
func respond(
    to prompt: String,
    options: GenerationOptions = GenerationOptions(),
    onPartial: (String) -> Void
) async throws -> ChatOutcome {
    do {
        let result = try await streamOnce(prompt, options: options, onPartial: onPartial)
        return ChatOutcome(text: result.text, metrics: result.metrics, didTrimContext: false)
    } catch let error as LanguageModelSession.GenerationError {
        guard case .exceededContextWindowSize = error else {
            throw AIKitError(error)
        }
        // 上下文撑爆了：裁掉早期对话、保住系统提示，用剩下的历史重建会话后重试一次。
        // 只重试一次——如果裁剪后仍然超限，说明单次提问本身就过长，重试没有意义。
        session = LanguageModelSession(
            model: .default,
            transcript: TranscriptTrimmer.trim(
                session.transcript,
                keepingRecentEntries: recentEntriesToKeep
            )
        )
        do {
            let result = try await streamOnce(prompt, options: options, onPartial: onPartial)
            return ChatOutcome(text: result.text, metrics: result.metrics, didTrimContext: true)
        } catch {
            throw AIKitError(error)
        }
    } catch {
        throw AIKitError(error)
    }
}
```

裁剪策略本身被抽成一个独立的纯函数 `TranscriptTrimmer.trim(_:keepingRecentEntries:)`（`WBAppleIntelligence/AIKit/Core/TranscriptTrimmer.swift`），完整实现如下：

```swift
nonisolated enum TranscriptTrimmer {

    /// 保留首条 instructions（若有）与最近 `count` 条其他条目。
    ///
    /// instructions 必须钉住：它是模型的角色设定，裁掉之后模型行为会当场跑偏。
    /// 只钉第一条是因为一个会话的系统提示只应该有一份，后面出现的同类条目按普通条目处理。
    static func trim(_ transcript: Transcript, keepingRecentEntries count: Int) -> Transcript {
        var pinnedInstructions: [Transcript.Entry] = []
        var others: [Transcript.Entry] = []

        for entry in transcript {
            if case .instructions = entry, pinnedInstructions.isEmpty {
                pinnedInstructions.append(entry)
            } else {
                others.append(entry)
            }
        }

        let keep = max(0, count)
        return Transcript(entries: pinnedInstructions + others.suffix(keep))
    }
}
```

三个设计决定，各自都有明确的理由：

1. **为什么必须钉住 instructions 条目。** `Transcript.Entry.instructions` 承载的是 `Prompts.helpdesk` 那段角色设定与回答规则——「你是企业内部 IT 支持助手」「涉及重置密码等敏感操作时提示走工单流程」这些约束。如果裁剪时把它当成普通历史条目一并按时间顺序裁掉，模型会在没有任何角色设定的情况下继续对话，行为当场跑偏（比如不再用编号列表、不再对敏感操作做提示）。所以裁剪函数把它单独摘出来、无条件保留，不占用 `keepingRecentEntries` 的名额。
2. **为什么只重试一次。** 裁剪后重建的会话如果依然超限，只有一种可能：不是历史太长，而是这一次的单条提示词（或者 `recentEntriesToKeep` 条历史加上这条提示词）本身就已经超过 4096 token。这种情况下再裁一次历史也无济于事——历史已经被砍到只剩 instructions，没有更多空间可以腾了。继续重试只是在浪费一次推理延迟，所以这里选择直接把第二次的失败当成最终失败抛出。
3. **为什么要在 UI 上显式提示裁剪，而不是静默处理。** `ChatOutcome.didTrimContext` 一路透传到 `ChatViewModel.didTrimContext`，再由 `ChatDemoView` 渲染成一条提示：

   ```swift
   if viewModel.didTrimContext {
       Label("早期对话已被裁剪以腾出上下文空间", systemImage: "scissors")
           .font(.caption)
           .foregroundStyle(.orange)
   }
   ```

   静默裁剪看起来对用户更「无感」，但代价是模型会突然「忘记」几轮之前聊过的内容——用户如果不知道发生了裁剪，会把这当成模型出现幻觉或者答非所问来投诉，而实际原因只是历史被自动清理了。显式提示把这次状态变化告诉用户，让「为什么它突然不记得前面说的了」这个疑问有一个诚实的答案，也让用户可以据此判断要不要开一个新会话。

## 6. 指标采集

`MetricsTimer`（`WBAppleIntelligence/AIKit/Core/GenerationMetrics.swift`）负责采样一次生成的耗时，两个实现细节都是刻意为之：

**为什么用 `ContinuousClock` 而不是 `Date`。** `Date` 基于系统的墙上时钟，会被用户手动改系统时间、时区切换、NTP 对时等因素影响，两次 `Date()` 相减在理论上可能得到负数或者跳变的耗时。`ContinuousClock` 是单调时钟，只会随真实流逝的时间前进，不受时钟调整影响，适合用来测量一段代码实际经过的时间。

**为什么 `Duration.components` 必须把 `attoseconds` 一起算进去：**

```swift
nonisolated extension Duration {
    var seconds: TimeInterval {
        let parts = components
        return TimeInterval(parts.seconds) + TimeInterval(parts.attoseconds) / 1e18
    }
}
```

`Duration.components` 拆出的是 `(seconds: Int64, attoseconds: Int64)` 两段整数，`attoseconds` 是 1e-18 秒量级的小数部分。端侧模型的首字延迟通常是几百毫秒级别，如果只取 `parts.seconds` 而丢掉 `attoseconds`，一次 320 毫秒的首字延迟会被直接截断成 `0` 秒——这不是精度损失，而是把这个指标里最有信息量的部分（亚秒级的响应速度）直接抹掉了。必须把两段加在一起才能保留住毫秒乃至更细的精度。

**`tokenCount(for:)` 的降级策略。** `SystemLanguageModel.tokenCount(for:)` 是 iOS 26.4+ 才有的 API（`swift symbolgraph-extract` 读出的 availability 标注为 `iOS 26.4`），用来统计一段文本占用的 token 数：

```swift
let promptTokens = try? await SystemLanguageModel.default.tokenCount(for: prompt)
let responseTokens = try? await SystemLanguageModel.default.tokenCount(for: latest)
```

这里用 `try?` 把失败结果降级为 `nil`，而不是让整次回答失败。理由是：token 计数是「锦上添花」的可观测性数据，不是这次对话能否完成的必要条件——用户要看到的是回答本身，token 数只是给到 `MetricsBar` 展示的辅助信息。如果因为这一次统计调用失败（比如模型资源临时不可用）就让整个 `respond` 抛错、把已经生成好的回答也搭进去，是本末倒置。`GenerationMetrics.tokensPerSecond` 同样遵循「缺数据就返回 `nil` 而不是 `0`」的原则（`WBAppleIntelligence/AIKit/Core/GenerationMetrics.swift`），因为 `0` 在指标展示里容易被误读成「卡住了」。

## 7. 踩坑记录

- **`concurrentRequests`——同一个 session 不支持并发请求。** 框架的 `LanguageModelSession.isResponding` 文档原文写得很直接：「You should not call any of the respond methods while this property is `true`. Disable buttons and other interactions to prevent users from submitting a second prompt while the model is responding to their first prompt.」如果不做这层拦截，用户在上一条回答还在流式输出时再次点发送，会直接触发 `LanguageModelSession.GenerationError.concurrentRequests`（映射为 `AIKitError.concurrentRequests`，文案「上一次生成尚未结束」）。`ChatViewModel.canSend` 与 `send()` 开头的 `guard !isResponding` 就是这道拦截：

  ```swift
  var canSend: Bool {
      !input.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty && !isResponding
  }
  ```

  `ChatDemoView` 的发送按钮绑定了 `.disabled(!isEnabled || !viewModel.canSend)`，从 UI 层面就不让这次点击发生，而不是等模型报错之后再兜底处理。

- **`rateLimited`——App 在后台时限流更严格。** `LanguageModelSession.GenerationError.rateLimited` 的框架注释是「This error will only happen if your app is running in the background and exceeds the system defined rate limit.」也就是说这个限流规则只在 App 处于后台时生效，前台交互式使用基本不会碰到；框架在 `streamResponse` 系列方法的文档里也专门提示：如果要在后台运行，应该改用非流式的 `respond(to:options:)` 来降低触发 `rateLimited` 的概率。本 Demo 是纯前台交互场景，`AIKitError.rateLimited` 的恢复文案「请稍后再试。App 进入后台时系统会更严格地限流。」就是为将来这个 Demo 被挪到后台任务、批处理等场景里复用时准备的提醒。

## 8. 性能数据

> **待真机实测**：首字延迟与 token 速率区间。测试方法：在已开启 Apple Intelligence 的 iPhone 15 Pro 及以上机型上，针对 `Prompts.helpdesk` 场景发送若干条不同长度的真实提问（例如「我的 MacBook 连不上公司 Wi-Fi 怎么办」），记录 `MetricsBar` 展示出的「首字」（`GenerationMetrics.firstTokenLatency`）与「速率」（`GenerationMetrics.tokensPerSecond`）数值，重复多次取区间范围，分别记录 `temperature` 为 0 与 1 时是否存在明显差异。
