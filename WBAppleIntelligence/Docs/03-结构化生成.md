# 03 结构化生成

对应代码：`WBAppleIntelligence/Features/TicketExtraction/TicketExtractionViewModel.swift`、`WBAppleIntelligence/Features/TicketExtraction/TicketExtractionDemoView.swift`、`WBAppleIntelligence/AIKit/Extraction/ServiceTicket.swift`、`WBAppleIntelligence/AIKit/Extraction/TicketExtractionService.swift`。

## 1. 场景与价值

`TicketExtractionDemoView` 对应的场景是企业 IT 服务台的工单录入：员工不填表单，只用一段口语描述遇到的问题（比如「投影仪连不上，HDMI 插上去没信号」），系统要把这段自由文本变成一张有固定字段的工单——标题、类别、优先级、影响人数、关键词、摘要——才能进入后续的分派、统计、SLA 计时等流程。`DemoRoute.ticketExtraction.scenario` 里的原话是：「服务台工单录入：把用户的口语描述实时抽取成强类型工单，边生成边填表。」（`WBAppleIntelligence/App/DemoRoute.swift`）

把自由文本变成结构化数据，传统做法通常是「提示词里要求模型输出 JSON，自己再 `JSONDecoder` 一遍」。这条路径必须自己承担一整套容错代码：

- 模型可能输出不闭合的括号、多余的解释性文字包裹着 JSON、字段名拼错、枚举值不在预期集合里——每一种情况都要单独判断、单独兜底；
- 字段类型不匹配（比如 `affectedPeople` 被模型写成字符串 `"8"` 而不是数字 `8`）需要额外做类型强转或二次校验；
- 一旦解析失败，通常只能整体重试或者向用户报错，因为你拿不到「这次输出到底哪里错了」的结构化信息。

`@Generable` 把这一整层容错代码直接删掉了：schema 由框架在解码阶段强制约束模型的输出，`ServiceTicket(_ content: GeneratedContent)` 要么给你一个字段类型、字段值域都满足约束的完整实例，要么抛出一个具体到「哪个字段、什么原因」的 `LanguageModelSession.GenerationError`（见第 8 节）。`DemoRoute.ticketExtraction.value` 的原话就是这个意思：「结构化输出由 schema 强约束，解析不会失败；录入耗时从分钟级降到秒级。」

## 2. `@Generable` 宏做了什么

`@Generable` 是一个同时挂了 `@attached(extension, ...)` 和 `@attached(member, ...)` 的宏，通过 `swift symbolgraph-extract` 读出的完整签名与文档是：

```
@attached(extension, conformances: Generable, names: named(init(_:)), named(generatedContent))
@attached(member, names: arbitrary)
macro Generable(description: String? = nil)
```

> Conforms a type to `Generable` protocol.

也就是说它做了两件事：

1. **`@attached(member, names: arbitrary)`**——往类型内部添加任意数量的成员。落到 `ServiceTicket` 上，合成的成员包括 `static var generationSchema: GenerationSchema`（`Generable` 协议要求的关联属性）和 `associatedtype PartiallyGenerated`（一个所有字段镜像为可选值的类型，见第 5 节）。
2. **`@attached(extension, conformances: Generable, names: named(init(_:)), named(generatedContent))`**——生成一个扩展，让类型遵循 `Generable`（进而遵循 `ConvertibleFromGeneratedContent` 与 `ConvertibleToGeneratedContent`），并在扩展里合成 `init(_ content: GeneratedContent) throws` 与 `var generatedContent: GeneratedContent { get }` 这两个具体实现。

框架对这两个协议要求的文档分别是：

> `ConvertibleFromGeneratedContent/init(_:)`：*"Creates an instance from content generated by a model. Conformance to this protocol is provided by the `@Generable` macro."*
>
> `ConvertibleToGeneratedContent/generatedContent`：*"This instance represented as generated content. Conformance to this protocol is provided by the `@Generable` macro."*

`ServiceTicket` 的完整代码（`WBAppleIntelligence/AIKit/Extraction/ServiceTicket.swift`）：

```swift
import FoundationModels

/// 从员工的自由文本描述中抽取出的一张 IT 服务工单。
///
/// 字段顺序不是随意排的：模型按声明顺序生成，流式填表时用户看到的填充次序就是这个顺序，
/// 所以把最能立刻确认「抽对了没有」的 title 放在最前面。
///
/// `@Generable` 会为该类型合成 `generationSchema`、`PartiallyGenerated` 以及
/// `init(_ content: GeneratedContent) throws`，schema 由框架强制约束模型输出，
/// 所以这里不需要写任何 JSON 解析与容错代码。
///
/// 显式 `nonisolated`：工程开启了 `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`，
/// 不加标注的类型会被隐式推断为 `@MainActor`，连同其协议一致性（如 `Equatable`）
/// 一起被主线程隔离，与 AIKit 其他纯值类型的约定不一致。
@Generable(description: "从员工的自由文本描述中抽取出的一张 IT 服务工单")
nonisolated struct ServiceTicket: Equatable, Sendable {

    @Guide(description: "一句话工单标题，控制在 20 个汉字以内，要具体到设备或系统")
    var title: String

    @Guide(description: "工单类别")
    var category: TicketCategory

    @Guide(description: "紧急程度")
    var priority: TicketPriority

    @Guide(description: "受影响的人数，只影响描述者本人时填 1", .minimum(1), .maximum(100_000))
    var affectedPeople: Int

    @Guide(description: "可检索的关键实体，如设备型号、系统名称、错误码，不要放形容词", .maximumCount(5))
    var keywords: [String]

    @Guide(description: "对问题的客观复述，不要添加原文没有的信息")
    var summary: String
}
```

`GenerationSchema` 本身的文档说明了它的定位：*"A type that describes the properties of an object and any guides on their values. Generation schemas guide the output of a `SystemLanguageModel` to deterministically ensure the output is in the desired format."*——「确定性地保证输出格式」这句话就是「不需要自己写解析容错」的框架侧根据。

## 3. `@Guide` 全部约束类型

`@Guide` 宏本身有三个重载，签名与文档（同样取自符号表）：

```
@attached(peer) macro Guide<T>(description: String? = nil, _ guides: GenerationGuide<T>...) where T : Generable
@attached(peer) macro Guide<RegexOutput>(description: String? = nil, _ guides: Regex<RegexOutput>)
@attached(peer) macro Guide(description: String)
```

> Allows for influencing the allowed values of properties of a `Generable` type.

真正提供约束能力的是 `GenerationGuide<Value>` 上的一组静态工厂方法，完整列表（按符号表导出顺序）：

- **`description`**——`@Guide` 自带的自然语言描述参数，本工程里每个字段都在用，例如 `@Guide(description: "工单类别")`。
- **`.constant(_ value: String) -> GenerationGuide<String>`**——*"Enforces that the string be precisely the given value."* 强制字符串等于某个固定值。
- **`.anyOf(_ values: [String]) -> GenerationGuide<String>`**——*"Enforces that the string be one of the provided values."* 强制字符串落在一个给定集合里；本工程用 `@Generable enum` 表达类别/优先级这类封闭集合（见第 4 节），没有用到 `.anyOf`，但它是应对「不想建一个新枚举、只是想约束几个字符串取值」场景的轻量替代。
- **`.pattern<Output>(_ regex: Regex<Output>) -> GenerationGuide<String>`**——*"Enforces that the string follows the pattern."* 用正则表达式约束字符串格式。

  **这里有一个必须写清楚的踩坑点：正则字面量在本工程 `SWIFT_VERSION = 5.0` 语言模式下必须写成 `#/.../#`，裸斜杠 `/.../` 会编译失败。** 这是本次任务里实测出的结论，用最小复现样例验证：

  ```swift
  @Generable
  struct Foo {
      @Guide(.pattern(/[A-Z]+/))
      var code: String
  }
  ```

  用工程实际的 `swiftc` 参数（`-swift-version 5`，`arm64-apple-ios26.0-simulator` target）对上面这段做 `-typecheck`，编译器报错：

  ```
  test2.swift:5:21: error: '/' is not a prefix unary operator
      @Guide(.pattern(/[A-Z]+/))
                      `- error: '/' is not a prefix unary operator
  ```

  原因是裸斜杠分隔的正则字面量在特定语法位置上与除法运算符存在解析歧义，`.pattern(` 紧跟的 `/` 被编译器当成了一个（并不存在的）前缀一元运算符去解析。把同一个字面量改写成扩展分隔符形式后，同样的 `-typecheck` 命令零错误通过：

  ```swift
  @Guide(.pattern(#/[A-Z]+/#))
  ```

  本工程当前的 `ServiceTicket` 没有字段需要正则约束（`title`／`summary` 都是开放文本，`keywords` 用的是 `.maximumCount` 而不是逐项格式约束），所以这条结论目前只是「验证过」而不是「代码里用到过」，但只要以后有字段需要加 `.pattern(...)`，必须直接写 `#/.../#`，不要按直觉写裸斜杠。

- **`.minimum` / `.maximum` / `.range`**——数值区间约束，`Int`／`Float`／`Double`／`Decimal` 各有一套重载：

  ```
  static func minimum(_ value: Int) -> GenerationGuide<Int>
  static func maximum(_ value: Int) -> GenerationGuide<Int>
  static func range(_ range: ClosedRange<Int>) -> GenerationGuide<Int>

  static func minimum(_ value: Float) -> GenerationGuide<Float>
  static func maximum(_ value: Float) -> GenerationGuide<Float>
  static func range(_ range: ClosedRange<Float>) -> GenerationGuide<Float>

  static func minimum(_ value: Double) -> GenerationGuide<Double>
  static func maximum(_ value: Double) -> GenerationGuide<Double>
  static func range(_ range: ClosedRange<Double>) -> GenerationGuide<Double>

  static func minimum(_ value: Decimal) -> GenerationGuide<Decimal>
  static func maximum(_ value: Decimal) -> GenerationGuide<Decimal>
  static func range(_ range: ClosedRange<Decimal>) -> GenerationGuide<Decimal>
  ```

  `ServiceTicket.affectedPeople` 用的是其中的 `Int` 重载：`@Guide(description: "受影响的人数，只影响描述者本人时填 1", .minimum(1), .maximum(100_000))`——同时给了下限（至少影响 1 人，即描述者本人）和一个足够大的上限（避免模型编出一个不合理的天文数字）。

- **`.minimumCount` / `.maximumCount` / `.count` / `.element`**——数组专用约束，四个都带 `where Value == [Element]` 约束：

  ```
  static func minimumCount<Element>(_ count: Int) -> GenerationGuide<[Element]>
  static func maximumCount<Element>(_ count: Int) -> GenerationGuide<[Element]>
  static func count<Element>(_ count: Int) -> GenerationGuide<[Element]>
  static func count<Element>(_ range: ClosedRange<Int>) -> GenerationGuide<[Element]>
  static func element<Element>(_ guide: GenerationGuide<Element>) -> GenerationGuide<[Element]>
  ```

  `ServiceTicket.keywords` 用的是 `.maximumCount(5)`：*"Enforces a maximum number of elements in the array. The bounds are inclusive."*——最多 5 个关键词，防止模型把整句话的名词都塞进去。`.element(_:)` 的文档给出的场景是对数组内每个元素再套一层约束，例如 *"you may want to generate an array of integers, where all the integers are in the range 0-9"*；本工程的 `keywords: [String]` 没有对元素做进一步约束，属于「用得到但暂未用到」的一类。

## 4. 枚举作为字段类型

`TicketCategory` 与 `TicketPriority` 都是 `@Generable enum`：

```swift
@Generable(description: "工单类别")
nonisolated enum TicketCategory: Equatable, Sendable {
    case hardware
    case software
    case network
    case account
    case other
}

@Generable(description: "工单紧急程度")
nonisolated enum TicketPriority: Equatable, Sendable {
    case low
    case medium
    case high
    case urgent
}
```

`@Generable` 加在枚举上时，效果相当于给这个类型生成了一份「只允许是这几个 case 之一」的 schema——本质上和 `.anyOf(_:)` 是同一件事，只是约束对象从字符串变成了强类型的 case，模型返回的内容会被强制解码成这几个 case 之一，拿到手的 `TicketCategory` 不可能是一个「集合之外」的值。

**为什么两个枚举都没有加 `CaseIterable`：** `@Generable` 是 `@attached(member, names: arbitrary)`，会给枚举合成任意数量的成员；`CaseIterable` 同样要合成 `allCases`。两者都在生成「概览全部 case」这一类语义相近的成员，一起使用时容易产生名字冲突或行为歧义（宏合成的东西发生冲突时，报错定位往往比手写代码的编译错误更绕）。工程选择手写一份不依赖任何协议合成的替代实现：

```swift
nonisolated extension TicketCategory {
    var displayName: String {
        switch self {
        case .hardware: "硬件"
        case .software: "软件"
        case .network: "网络"
        case .account: "账号权限"
        case .other: "其他"
        }
    }

    /// 供测试与界面遍历使用。
    ///
    /// 不加 `CaseIterable`：`@Generable` 会给枚举合成成员，与 `CaseIterable` 的
    /// `allCases` 合成同时存在时容易产生歧义，手写一份反而更省心。
    static let allDisplayCases: [TicketCategory] = [.hardware, .software, .network, .account, .other]
}
```

`allDisplayCases` 同时承担两个职责：`ServiceTicketTests.categoryHasDisplayName(_:)` 用它做参数化测试遍历每个 case（`WBAppleIntelligenceTests/ServiceTicketTests.swift`），未来如果要在界面上做「类别选择器」之类的下拉列表，也直接复用这份数组，不需要再手写一次 case 列表。

## 5. 流式填表

结构化抽取与自由文本对话在流式 API 上的关键差别，集中在 `LanguageModelSession.ResponseStream<Content>.Snapshot` 这一层。框架文档：

> `Snapshot`：*"A snapshot of partially generated content."*
> `Snapshot.content`：*"The content of the response."*，类型是 `Content.PartiallyGenerated`。
> `Snapshot.rawContent`：*"The raw content of the response. When `Content` is `GeneratedContent`, this is the same as `content`."*

对自由文本对话（`Content == String`），`String.PartiallyGenerated` 就是 `String` 自己，`snapshot.content` 直接是当前已生成的完整字符串（见文档 02 第 2 节）。但对 `Content == ServiceTicket`，`ServiceTicket.PartiallyGenerated` 是一个由 `@Generable` 合成的镜像类型——**六个字段全部变成可选值**：`title: String?`、`category: TicketCategory?`、`priority: TicketPriority?`、`affectedPeople: Int?`、`keywords: [String]?`、`summary: String?`。已经生成完的字段有值，还没轮到的字段是 `nil`。这正是「边生成边填表」的数据来源：

```swift
func extract(
    from text: String,
    onPartial: (ServiceTicket.PartiallyGenerated) -> Void
) async throws -> TicketOutcome {
    var timer = MetricsTimer()
    var lastRawContent: GeneratedContent?

    do {
        let stream = session.streamResponse(to: text, generating: ServiceTicket.self)
        for try await snapshot in stream {
            timer.markFirstToken()
            // 留住 rawContent 而不是 content：流结束后要用它还原成完整的 ServiceTicket，
            // PartiallyGenerated 的字段全是可选值，无法直接当最终结果用。
            lastRawContent = snapshot.rawContent
            onPartial(snapshot.content)
        }
    } catch {
        throw AIKitError(error)
    }

    guard let lastRawContent else { throw AIKitError.emptyResponse }

    let ticket: ServiceTicket
    do {
        ticket = try ServiceTicket(lastRawContent)
    } catch {
        throw AIKitError(error)
    }
    // ...
}
```

（完整实现见 `WBAppleIntelligence/AIKit/Extraction/TicketExtractionService.swift`。）

`TicketExtractionDemoView.ticketForm` 把这份 `partial` 直接接到界面上，用「有最终结果就显示最终结果，没有就退回显示流式中间态」的写法逐字段渲染：

```swift
field("标题", viewModel.ticket?.title ?? viewModel.partial?.title)
field("类别", (viewModel.ticket?.category ?? viewModel.partial?.category)?.displayName)
field("优先级", (viewModel.ticket?.priority ?? viewModel.partial?.priority)?.displayName)
field("影响人数", (viewModel.ticket?.affectedPeople ?? viewModel.partial?.affectedPeople).map { String($0) })
field("关键词", (viewModel.ticket?.keywords ?? viewModel.partial?.keywords)?.joined(separator: "、"))
field("摘要", viewModel.ticket?.summary ?? viewModel.partial?.summary)
```

值得记录的一个实测细节：`viewModel.partial?.keywords` 的类型是 `[String]?`（数组整体可选，元素类型 `String` 不可选），不是 `[String?]?`。这一点在写文档前没有查到框架侧的书面说明，是靠这段代码本身能否通过类型检查反推出来的——`(viewModel.ticket?.keywords ?? viewModel.partial?.keywords)?.joined(separator: "、")` 这一行如果 `keywords` 的实际类型是 `[String?]?`，`.joined(separator:)` 会因为数组元素不是 `String` 而编译失败；本工程的 clean build 零错误通过，反过来确认了 `PartiallyGenerated` 里数组字段的可选层级只包在整个数组外面，不会包到每个元素上。

**为什么最终结果必须从最后一个 `snapshot.rawContent` 还原，而不能直接拿 `PartiallyGenerated` 当结果用：** `PartiallyGenerated` 存在的意义就是「允许字段暂时是空的」，它的类型签名（六个字段全 `Optional`）决定了即使生成已经正常结束、所有字段事实上都有值，它在类型系统里也只是「一堆 optional，理论上仍可能是 nil」，没有任何办法把它转换成一个字段全部非可选的 `ServiceTicket`。真正代表「这次生成已经完整结束」的是 `Snapshot.rawContent: GeneratedContent`——它不是镜像类型，是模型输出的原始结构化内容，`ServiceTicket(_ content: GeneratedContent) throws` 只接受这个类型。所以 `extract(from:onPartial:)` 里每次迭代都用 `lastRawContent = snapshot.rawContent` 覆盖式更新，循环结束后用最后一次的 `lastRawContent` 去调用 `ServiceTicket(lastRawContent)`，这一步才是真正把「生成完毕」变成一个字段确定、可以塞进 `TicketOutcome.ticket` 的强类型值。

## 6. 字段顺序的实际影响

`ServiceTicket` 里字段的声明顺序不是随意排列的，`title` 放在最前面这件事在源码注释里写得很直接：

```swift
/// 字段顺序不是随意排的：模型按声明顺序生成，流式填表时用户看到的填充次序就是这个顺序，
/// 所以把最能立刻确认「抽对了没有」的 title 放在最前面。
```

模型按 `@Generable` 类型声明字段的顺序逐个生成，`title → category → priority → affectedPeople → keywords → summary`，这个顺序会原样反映在 `PartiallyGenerated` 逐步被填充的过程里，也就是用户在 `ticketForm` 里实际看到字段变亮的顺序。这意味着字段声明顺序其实是一个产品决策，不只是代码风格问题：**最应该让用户尽早确认「模型有没有理解对」的字段，要放在最前面。** `title` 是一句话摘要，通常一眼就能判断「这次抽取对不对路」，所以排第一；反过来如果把 `summary`（篇幅最长、需要读完才能判断对错的字段）放在最前面，用户要多等一轮生成才能做出「对/不对」的第一判断，体验上是倒退的。这个顺序同时决定了 Task 10 单元测试（`ServiceTicketTests`）和本文档里 JSON 示例的字段书写顺序——两处都刻意保持了和源码声明一致的顺序，而不是按字母或随意排列。

## 7. schema 也要占预算

`SystemLanguageModel.tokenCount(for:)` 有一个专门接受 `GenerationSchema` 的重载：

```
nonisolated(nonsending) final func tokenCount(for schema: GenerationSchema) async throws -> Int
```

> Returns the token count for the specified schema.

`TicketExtractionService.extract(from:onPartial:)` 把这个重载和普通文本重载一起用上了：

```swift
let promptTokens = try? await SystemLanguageModel.default.tokenCount(for: text)
let schemaTokens = try? await SystemLanguageModel.default.tokenCount(
    for: ServiceTicket.generationSchema
)

return TicketOutcome(
    ticket: ticket,
    metrics: timer.finish(
        // schema 本身也要占提示词预算，把两部分加起来才是真实的输入开销。
        promptTokenCount: sum(promptTokens, schemaTokens),
        responseTokenCount: nil
    )
)
```

原因是 `streamResponse(to:generating:includeSchemaInPrompt:options:)` 默认会把 schema 本身注入到提示词里去约束模型（`includeSchemaInPrompt` 默认 `true`，见第 8 节），这部分内容和输入文本一样要占用 4096 token 的上下文窗口。如果指标只统计 `text` 的 token 数、不把 schema 算进去，`MetricsBar` 展示的「输入」数字会明显偏小，看起来还有很多余量，但实际能留给回答（这里是留给生成结果本身）的窗口比这个数字暗示的要小。字段越多、每个字段的 `description` 写得越长，`ServiceTicket.generationSchema` 序列化后占用的 token 就越多——这也是为什么 `@Guide(description:)` 的文案要精炼、没必要把使用规则也塞进 description 里（那类规则更适合放在 `Prompts.ticketExtraction` 的 instructions 里，只在会话初始化时算一次，而不是跟着 schema 在每次生成时重复计费）。

> **待真机实测**：`ServiceTicket.generationSchema` 实际占用的 token 数。测试方法：在已开启 Apple Intelligence 的真机上运行一次 `TicketExtractionDemoView` 的抽取流程，读取 `MetricsBar` 展示的「输入」数值（对应 `GenerationMetrics.promptTokenCount`，即 `sum(promptTokens, schemaTokens)`），并额外在代码里单独打印 `schemaTokens` 一项，得到 schema 单独占用的 token 数；再对比修改 `@Guide` 的 description 文案长度前后这个数字的变化幅度。

## 8. 踩坑记录

- **`decodingFailure` 与 `unsupportedGuide` 的区别。** 两者都被 `AIKitError.init(_:)` 映射成独立的 case（`WBAppleIntelligence/AIKit/Core/AIKitError.swift`），但触发时机完全不同：

  > `decodingFailure(_:)`：*"An error that indicates the session failed to deserialize a valid generable type from model output. This can happen if generation was terminated early."*
  >
  > `unsupportedGuide(_:)`：*"An error that indicates a generation guide with an unsupported pattern was used."*

  `decodingFailure` 是**运行时**问题：schema 本身没有错，但这一次生成提前终止（比如被截断在数组或字符串中间），导致最终收到的内容拼不出一个合法的 `ServiceTicket`——这类问题通常靠重试解决，`AIKitError.decodingFailure` 的恢复建议是「请简化结构定义或降低字段数量后重试」。`unsupportedGuide` 是**定义时**问题：`@Guide` 里写了当前模型不支持的约束模式（例如某些正则语法、某些数值范围组合），这类错误不会因为重试而消失，必须去改 `ServiceTicket` 的 `@Guide` 定义本身。两者的恢复文案也因此不同——`decodingFailure` 引导「重试」，`unsupportedGuide` 引导「检查约束定义」。

- **`includeSchemaInPrompt` 的取舍。** `streamResponse(to:generating:includeSchemaInPrompt:options:)` 的这个参数默认 `true`，框架文档给出的建议是：

  > *"Consider using the default value of `true` for `includeSchemaInPrompt`. The exception to the rule is when the model has knowledge about the expected response format, either because it has been trained on it, or because it has seen exhaustive examples during this session."*

  也就是说，只有在两种情况下才值得考虑关掉它：模型本身已经在训练阶段见过这个格式，或者当前会话里已经给过足够多次高质量的示例，模型已经「记住」了期望的输出形态。`TicketExtractionService` 没有做过这类预热或示例注入，`ServiceTicket` 这个 schema 也不属于模型训练时见过的通用格式，所以保持默认的 `true`——代价是每次生成都要多付出 schema 本身的 token（见第 7 节），换来的是生成结果符合 schema 的可靠性，这笔账在「录入耗时从分钟级降到秒级」的场景里是划算的。
